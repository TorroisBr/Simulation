## Reconciliation result

The current test manifest defines a 299-row reference fixture with:

`61 + 22N + (N-M) + P + 4C`

where `N` is the installed NPC count, `M` the count of NPCs bound to a registered Person, `P` the registered Person count, and `C` the installed City count. For the current authored fixture (`N=10, M=0, P=0, C=2`), the total is `61 + 220 + 10 + 0 + 8 = 299`.

The current manifest is independent of the census protocol's expected/registered dictionaries: it checks exact section IDs, role, schema, provider identity, nonnegative cardinality/revision, stable repeated readings, and zero cardinality for `ExplicitlyEmpty` rows. Roster/materialization witnesses exercise selected changes to `N`, `M`, and `P`. This is a strong reference-fixture and selected-transition check. It is not a generic traversal of every object in the runtime graph, a proof of every supported writer, or evidence for every possible City/owner transition.

Older canonical snapshots record a 275-row census, and the earlier owner ledger records a 278-row equation (`68 + 20N + U + P`). Those are historical protocol versions. The current test manifest supersedes them with the 299-row equation above: 61 non-City fixed rows, 22 per live NPC, conditional unbound-NPC residence rows, Person rows, and four rows per City. Do not mix the historical fixed/dynamic decomposition with the current one.

The old G crosswalk describes a 23-operation inventory, and the current [registered operation matrix](PHASE12_B_DAILY_V1_REGISTERED_OPERATION_MATRIX.md) has 24 IDs. Its final addition is `runtime.person.parentage`, implemented through the supported `SimulationRuntime.TryAddParentage` / `TryRemoveParentage` facades. The matrix final paragraph also still presents `278 fixed-section baseline + 20N + U + P` as the current census count; that count sentence is stale. The 24 operation IDs remain the current operation reference, while the current test manifest supersedes the matrix's old 278/20N count wording with the 299-row equation above.

Current tests cover the exact set, repeated witness stability, selected NPC roster changes and Person materialization; they do not generically walk the graph or establish every City/owner transition.
2. **Write and epoch closure:** finish the row-to-commit/enclosing-operation map for Crime/Social appraisal and any supported direct Crime/Justice/Military path. The operation matrix's 24 IDs are a known set, not an exhaustiveness certificate.
3. **Current package revalidation:** recheck B–F interfaces, revisions/cardinalities, bindings, failure semantics, and dependency order at the current canonical tips. Earlier C–F and target-zero audits were based on older canonical snapshots; retain them as useful interface evidence, but refresh conclusions where owner package code changed.
4. **Fresh target-owner witnesses:** integrate exact target checks for P8-C/D, the two global receipt caches, both per-NPC P18 receipt owners per staged NPC, Crime and Justice sentinels, and ActorChoice temporal state. Existing constructors/providers do not prove that a future G coordinator calls them in the required order.
5. **Restored boundary and publication:** implement fresh target-bound admission preserving the source day and successful core sequence, with a completed-boundary token bound to the healthy reconstructed runtime; move the remaining `TesteSimulacao` consumers to one active-session root and show one reference exchange.
6. **Whole-graph proof:** admission/rejection, whole-graph reference validation, failure atomicity, no replay/repeated effects, and continuation parity remain implementation and validation obligations under the accepted G design.
