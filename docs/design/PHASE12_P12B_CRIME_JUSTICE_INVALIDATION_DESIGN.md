**Design state:** the daily-boundary-only revision passed exact-tip review at `5d5539dd198d74324eb7ecfb296819f4f38d83e9`. ## Purpose and scope

After the population lifecycle promotion, the Phase 12 State and blocker matrix still name direct NPC MoneyAccount/Inventory invalidation as the next work. That statement is stale. Code commit c49f957e45c3059231e9ec66e4010a7c3a389988 is an ancestor of the current P12 canonical and its code tree is 627af2fbd7f93e0025106ee5ba87e72bae6c4ed2. The older remote implementation ref 766137aea8535c1d8f6e5529856228db6890e718 has the same tree, so it is retained historical evidence and must not be re-delivered.

The highest-impact remaining selected-profile gap supported by the current source map is the legacy daily Crime/Justice mutation path. GeneralTest enables Crime and GuardCrime, and the runtime advances already-established hidden state and Justice records every day. `AdvanceDayAfterClockAdvance` continues into normal, ActorChoice, and scheduled-directive action execution after the four legacy calls; those paths can mutate the same NPC status and Justice owners before the outer `runtime.advance-day` operation exits. This design therefore covers the four legacy calls and the same-day action writes to those exact owners. It adds no crime, arrest, escape, or other gameplay rule, and it does not cover other CrimeSocialAppraisal owners.

P12-B remains INCOMPLETE, P12-A remains WAIT_DEPENDENCY, P13 remains BLOCKED, and Phase 12 remains open. No capture eligibility, complete owner or operation coverage, global quiescence, export, hydration, or P12-A/P13 readiness follows from this design or a future implementation of it.

## Current source contract

The accepted UnityBootstrap-Daily-v1 profile resolves the GeneralTest configuration with Economy, Merchant, GuardCrime, and Crime enabled. The published runtime contains one JusticeSystem and the configured CrimeSystem and GuardSystem providers. The selected profile does not compose the P18 timeline.

At the daily runtime boundary, SimulationRuntime calls these legacy methods in this exact order:

1. JusticeSystem.BeginDay()
2. CrimeSystem.AdvanceHiddenStatuses(npcRuntimes)
3. JusticeSystem.AdvanceSentences(npcRuntimes)
4. JusticeSystem.SyncWantedStatuses(npcRuntimes)

The selected path does not call the receipt-backed P18 prepared-step commit methods for those effects. Their P18 step revisions and receipts are separate state and cannot substitute for P12 invalidation of these legacy calls.

JusticeSystem owns two mutable, variable-size collections: wanted records and prison sentences. The selected implementation must observe the actual current contents and mutations. It must not assume one warrant or one sentence per NPC, or assume that startup emptiness bounds evolved state. Each retained row must continue to reference its actual target NPC and City owner; counts may be zero or greater than one over an NPC's history.

NpcRuntime owns the hidden-day counter and the current-status collection. The live roster has exactly one NpcRuntime per registered RuntimeId at each census boundary; its total cardinality follows the already-promoted roster reconciliation. CurrentStatus is a variable-size ordered list of status-definition references. Preserve its actual count and order, and do not infer uniqueness from AddStatus, because constructor/bootstrap paths use AddRange. Hidden-day state is one scalar per registered RuntimeId.

Production source does not mutate CurrentStatus through the public list from outside NpcRuntime; normal writes use AddStatus and RemoveStatus. The implementation will expose CurrentStatus as IReadOnlyList backed by a cached read-only wrapper, update the few consumers that require List to consume IReadOnlyList, and route test/setup writes through NpcRuntime methods. This removes the current bypass without adding a security boundary; P19 has not delivered a public mod API.

This changes the declared C# property type and requires the repository's consuming assemblies to recompile. The current Unity runtime types are not yet a stable public extension contract under the P19 proposal; this implementation does not deliver, version, or claim compatibility for the deferred P19 API/loader. If inspection finds a separately supported external consumer contract for the mutable List type, stop and redesign this seam before implementation rather than silently treating that external contract as absent.

CrimeSystem and JusticeSystem also contain P18 receipt-backed step state. Under this P12 profile that state must remain explicitly empty; a nonempty receipt set or nonzero step revision is unsupported profile state and must not be silently treated as captured by this slice. The P18 temporal state contract remains separate.

After `BeginSimulationDay`, the same `runtime.advance-day` operation continues through ordinary actor turns. `TryExecuteAction` dispatches the composed CrimeSystem and GuardSystem providers and invokes `INpcActionFailureHandler` on failed Crime attempts; successful action status effects run later in `TryExecuteCurrentAction`, after any provider-specific scope has returned. Requested-action directives use that same path. A forced Escape directive calls `JusticeSystem.ApplyEscapeSuccess` directly, applies action statuses, and only then marks the directive succeeded. These are selected-profile writes to the proposed status/hidden and Justice owners and must not be left with advanced local revisions but stale P12 baselines.

Use owner-specific admission scopes at those existing call sites. The provider scope covers the Crime/Guard provider and its failure handler; the success-status scope covers the actor and optional action target after the provider returns; the forced-Escape scope covers its Justice transition and action statuses before the directive is marked succeeded. Each scope binds the exact selected NPC/Justice owners and rejects a stale baseline before the provider or first status write. For each committed status or Justice leaf, preflight its current baseline and one epoch slot immediately before mutation, then notify that exact section immediately after the leaf commits. If notification fails after a domain write, fault the runtime and preserve the committed local change; do not roll it back. Do not defer a same-day action notification: an independent account, event, sequence, allocator, travel, merchant, ActorChoice, or directive notification inside the same action could consume the last epoch slot first. Do not reserve the protocol epoch or open a nested registered operation around these scopes. Preserve the existing call order and partial-commit behavior.

CrimeSocialAppraisalWorldState and its TheftOutcomeStore, CrimeKnowledgeStore, and SocialReactionStore are composed and some actor actions can write them. They remain explicit uncovered owner families. This design claims neither their P12 census nor complete Crime/Justice operation coverage. Direct mutation APIs on a P12-bound status/Justice owner must either join one of the exact reviewed contexts or reject before changing authoritative state; non-P12/unbound behavior remains unchanged. Receipt-backed P18 methods remain outside this selected Daily profile and must continue to fail the explicit-empty receipt admission check if state appears.

## Owner and cardinality contract

| Selected fact | Exact owner identity | Cardinality assumption | Local change evidence |
|---|---|---|---|
| NPC hidden-day counter and current status list | Exact NpcRuntime selected by RuntimeId | One NpcRuntime per current registered RuntimeId; dynamic roster count is reconciled at the existing census boundary. Status rows are zero-or-more and retain actual order/count. | Add p12b.npc-status-crime-state/<RuntimeId>, schema 1, with a local revision on NpcRuntime. This is an invalidation witness, not a second export DTO; P12-D/E later assigns each serialized NPC fact exactly once. Do not alias it to the existing life-state, residence, MoneyAccount, or Inventory section. |
| Wanted records and prison sentences | Exact JusticeSystem instance published by this SimulationRuntime | Exactly one JusticeSystem per selected runtime. Each internal collection is zero-or-more; there is no one-row-per-NPC or one-row-per-City rule. | Add p12b.justice-records, schema 1, with one Justice-owned local revision covering every successful legacy mutation of either collection and each retained row's mutable fields. The provider verifies exact owner reference and reports both actual collection counts; null rows or target/City links that do not resolve to the current selected owners fail census validation. |
| P18 receipt-backed Crime/Justice step state | Exact composed CrimeSystem and JusticeSystem instances | One of each when their selected effective configuration composes them; P18 receipt dictionaries/revisions remain empty in this P12 profile. | Add p12b.crime-p18-receipts and p12b.justice-p18-receipts, schema 1, each cardinality one and exact-owner-bound; reject nonempty receipts or nonzero P18 step revisions. A later P18 receipt write is not admitted as P12 coverage by this design. |

The Justice record rows are members of one singleton JusticeSystem owner in this P12-B witness; they are not separate owners with per-NPC cardinality. The P12-B witness checks dynamic list counts, row validity and local revision. It does not invent row identity or provide an export DTO. P12-E must define stable identities and the sentence-to-warrant relation encoding before Justice state can be exported or hydrated. Dynamic row counts are sampled values, not permanent cardinality promises.

## Bounded implementation contract after design review

1. Add the exact per-NPC status/hidden and singleton Justice census sections in the table. Add p12b.npc-status-crime-state/<RuntimeId> local revisions on NpcRuntime and p12b.justice-records local revision on JusticeSystem. Preflight capacity before each supported commit; do not increment on rejected calls or semantic no-ops. Make CurrentStatus a read-only view backed by a wrapper so production code cannot mutate the live List outside owner methods.
2. Bind exact providers to the selected runtime composition. Verify reference identity against the published NpcRuntime roster, JusticeSystem, and CrimeSystem; reconcile roster-derived NPC sections through the existing census path.
3. Add required explicit-empty receipt sections p12b.crime-p18-receipts and p12b.justice-p18-receipts, each cardinality one and bound to the exact owner. Reject the selected P12 profile if either owner has nonempty P18 receipts or a nonzero P18 step revision.
4. Use the existing single `runtime.advance-day` protocol operation held by `TryAdvanceDay` and `TryAdvanceDays`; do not call `TryEnterOperation` for any of the four nested legacy methods. Immediately before each legacy method, validate its exact owner baselines and reserve one mutation-epoch increment with `TryReserveMutationEpochCapacity` while the outer operation is the sole active registered operation. The method is a bounded commit boundary inside that existing operation, not a new registered protocol operation. After it returns, notify once with the exact sections whose owner revisions changed, consuming the reservation; if it made no semantic mutation, release the reservation without advancing the epoch. Preserve the call order, repeated `SyncWantedStatuses` call, and normal logging.
5. Preserve existing partial-commit behavior. If a legacy call commits some row/NPC changes and then throws, notify the exact sections whose revisions changed using that call's reservation, then rethrow the original domain exception. If P12 notification fails after a domain commit, fault the runtime according to the existing protocol. Do not add rollback or change Justice/Crime behavior.
6. Add a narrow Crime/Guard action-owner admission scope around only the selected composed provider invocation and its `INpcActionFailureHandler` path inside `TryExecuteAction`. It binds the exact actor status section, the exact registered target status section when present, and `p12b.justice-records`; verify provider/owner reference identity and validate all applicable baselines before entering the provider. Each subsequent status/Justice leaf must revalidate its own current baseline and epoch capacity immediately before writing, increment its local revision only for an actual change, and notify its exact section immediately after commit. Do not defer notification, open a registered operation, or hold an epoch reservation. Any MoneyAccount/Inventory, Event/RecordSequence, RuntimeIdAllocator, Travel, Merchant, ActorChoice, directive, or other owner notification made by the same call must still follow its existing path exactly once. This preserves capacity for independently notifying owners and prevents a later callback from consuming the last slot before the status/Justice write.
7. Wrap `ApplySuccessStatusChanges` in a separate narrow status-owner admission scope around the exact actor and optional target, after `TryExecuteAction` has returned and after any provider-specific operation scope is disposed. This applies to autonomous and ActorChoice-selected actions and requested-action directives. Validate all participating status baselines before the first write, then apply the same per-leaf preflight, local-revision, and immediate-notification rule. Do not duplicate the separate ActorChoice or provider notifications.
8. Wrap forced Escape's `ApplyEscapeSuccess` and its action-status effects in the corresponding Justice/status admission scope; notify each changed leaf immediately after commit and before `directive.MarkSucceeded` or the failure transition on a rejected result. ScheduledDirective's own terminal-state notification remains independent. Do not alter the accepted Escape result or directive outcome.
9. Bind the owner-local mutation callbacks to the exact P12 runtime. During a daily reserved boundary they advance local revisions and collect sections for that boundary's one reserved notification; during an action scope they preflight and notify each actual section change immediately. Outside a supported selected-profile boundary/scope, a P12-bound status or Justice write must fail before changing authoritative state. Preserve unbound/non-P12 behavior. Do not intercept or suppress unrelated section notifications.
10. Cover indirect mutable-row writes. `WantedRecordRuntime.AddPenalty`/`Resolve` and `PrisonSentenceRuntime.AdvanceDay`/`RegisterFailedEscape`/`ClearArrestedToday` must report through the exact owning JusticeSystem callback, including when reached through returned active-warrant rows or retained sentence rows. Bind each row to its Justice owner when created; reject a mismatched or unsupported P12-bound row mutation before its write. Bind the P12 receipt owner to the CrimeSystem/JusticeSystem admission hooks and reject receipt-backed `TryCommit*` writes on the P12 Daily profile before mutation, preserving the explicit-empty receipt sections.
11. Do not add a general operation/batch framework. Keep at most one Crime/Justice admission scope active on the runtime owner thread; reject/fault accidental overlap with an incompatible existing context before mutation. Daily boundaries release their single reservation in `finally`; action scopes clear their authorization context in `finally` and never defer notifications. Preserve actual domain call order, no-op semantics, partial commits, and unbound behavior.

The implementation sequence remains bounded to the four daily legacy calls plus the exact status/Justice writes made later in that same selected `runtime.advance-day` actor-turn path. It does not claim a new P12 operation for an individual actor action or complete action changed-owner sets. Other owners touched by Theft or related Crime paths, especially CrimeSocialAppraisal stores, remain separate blocker rows.

## Dependency-ordered implementation sequence

- **CJ-1 — owner census and local revisions:** exact per-NPC condition/status witness, exact singleton Justice witness, explicit-empty P18 receipt evidence, and local revisions at the underlying committed mutations. Tests establish real roster and row cardinalities, including multiple historical rows for the same NPC/City where the model permits them.
- **CJ-2 — selected daily integration:** bind the exact providers and cover the four existing runtime calls in order as sequential mutation boundaries inside the one existing `runtime.advance-day` operation, using per-call epoch reservations and committed changed-section sets.
- **CJ-3 — same-day Crime/Guard provider scope:** cover composed Crime/Guard provider calls and failure handlers inside the already-active daily operation, including committed failure penalties. Notify each selected owner leaf immediately; do not hold a protocol epoch reservation or capture unrelated callbacks.
- **CJ-4 — post-provider status and forced Escape scopes:** cover successful actor/target status changes and the forced Escape directive's Justice/status commit before its terminal directive transition.

CJ-1 through CJ-4 share NpcRuntime, JusticeSystem, ContinuationCensusProtocol, SimulationRuntime, and bootstrap-composition ownership. They are sequential sub-slices, not parallel writers. Read-only review of the source matrix is safe in parallel. Other CrimeSocialAppraisal owner sections remain visible blockers and are not silently covered by these scopes.

## Required validation for an implementation candidate

- Focused tests for current-roster membership/cardinality, exact Justice owner identity, zero/many wanted and sentence rows, stable target/City resolution, NPC status order/count, read-only status access, mutable warrant/sentence row callbacks through public accessors, and empty versus populated P18 receipts. Verify every public row/status/hidden-state mutator rejects unsupported P12-bound direct writes before mutation and preserves existing unbound behavior.
- Focused tests for each of the four daily calls through both `TryAdvanceDay` and `TryAdvanceDays`: exactly one active registered operation, changed owner revisions, unchanged/no-op behavior, exact changed sections, one reserved epoch per bounded call, owner-thread and stale-baseline rejection before writes, revision/epoch exhaustion, and partial commit followed by exception.
- Focused selected-profile actor tests for Crime Hide/Theft/Escape and failed Escape, Guard arrest, ordinary and ActorChoice-selected success-status effects, requested-action directives, and forced Escape. Assert the relevant NPC/Justice local revisions and section notifications, exact actor/target ownership, and that existing unrelated account/Inventory, Event/RecordSequence, RuntimeIdAllocator, Travel, Merchant, ActorChoice, and ScheduledDirective callbacks still run exactly once.
- Test that a returned failure with committed state and a partial-commit exception notify each already-committed selected leaf before exit/rethrow; a no-op does not advance the shared epoch; a mismatched or unsupported direct write to a P12-bound owner rejects before mutation; and unbound provider behavior remains unchanged. Exercise near-saturation behavior for owner revisions and the mutation epoch across independent notifications in the same action: each selected leaf must recheck its own current capacity immediately before the write and notify immediately after commit; no selected write may depend on capacity remaining after a later callback.
- Regression tests for Population lifecycle invalidation, actor status semantics, Crime hidden-day timing, Justice sentence/warrant ordering, and existing P18 receipt-backed steps.
- ALL EditMode, official Smoke, and git diff --check on the exact code tree; retain logs/XML and hashes. Re-run integration validation if shared runtime/provider composition changes.
- Independent exact-tip code review after implementation; include the exact architecture and alignment refs and check that the review tree matches the validation tree.

## Exclusions and remaining gates

This design does not add concrete Crime/Justice gameplay, new arrest or crime rules, new actor-control/security boundaries, historical replay, P12 export/hydration, P12-A readiness, complete P12-B owner or operation coverage, a complete shared epoch, global quiescence, P13 readiness, or Phase 12 closure. It covers only the specified selected-profile writes to NPC status/hidden and the singleton Justice record owner during the legacy daily sequence and its actor-turn portion. It does not cover CrimeSocialAppraisal stores, general Crime/Guard APIs outside the exact bound contexts, P18 temporal steps, P20 activities, P19 loader/API work, Lab UI, or a combined P10/P14 bootstrap profile.

P12-B work remains inside the accepted prerequisite capability authority recorded by the P12 Brief. After independent review, implementation may proceed only if the reviewer confirms the exact owner/cardinality and partial-commit design against current architecture, State, and source. If review finds a missing semantic choice rather than a technical gap, keep this track blocked and identify that exact decision; independent Phase work can continue.
