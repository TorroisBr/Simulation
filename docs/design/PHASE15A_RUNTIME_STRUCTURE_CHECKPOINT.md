# P15-A — One runtime structure at an existing Location

**Status:** candidate bounded checkpoint and technical design for independent review. **Architecture base:** `da34d50bd7831ac3eefab31e925492ede8dded5c`. **Product scope:** explicitly approved on 2026-10-03. This document grants no implementation or canonical promotion.

## Proof and selected profile

After the first truly simulated boundary, one explicit runtime construction operation creates one inert proving structure at an already registered canonical `LocationId`. The structure is a domain fact with stable `StructureId`, compatible definition/revision and creation boundary. It has no production, shelter, ownership transfer, population, combat, political or economic effect. The synthetic proving definition is an implementation fixture, not a general building catalog or player gameplay choice. There is no construction duration, workforce or P20 activity. The operation can be invoked by a controlled simulation fixture through ordinary runtime authority; no Actor/GM command surface is introduced. If a future external input invokes it, its payload, authority, logical boundary and order join the causal inventory before any durable use.

The proving world contains an existing P8-A registered `LocationRecord` and anchor Hex before this operation. P15-A does not mint a Hex, Location, City or region; it does not invoke genesis or retrofit. The structure's `LocationId` is the factual placement reference, resolved through the single `SpatialAuthorityStore`. No second spatial placement store or duplicate anchor is created. The owner of structure existence, identity, definition and creation boundary is one new bounded structure authority; a presentation object/diagnostic event is derived from it. A successful construction is an instantaneous committed creation at a logical boundary, not a start that promises later completion.

## Operation contract and owner

The implementation surface is a new domain file `RuntimeStructureTruth.cs` with immutable `StructureId` and `StructureRecord` values and one `StructureStore`. `StructureStore.TryCreateStructure` is the sole creation operation; `SimulationRuntime` composes it only in an explicit P15-A proving profile and supplies the established mutation guard and logical boundary. Unity presentation may only read it. One immutable `P15A-ProvingStructure/v1` definition is bundled with that profile; no registry or catalog is introduced. Focused EditMode tests own the fixture. Existing worlds require no migration because the profile is new and opt-in. The operation contract is:

1. Receive a stable `StructureId`, proving definition identity/revision, existing `LocationId`, and the operation's logical boundary/order. The proving fixture supplies the ID explicitly; there is no implicit Unity instance ID or new global allocator counter. A later allocator must retain its sequence and branch semantics.
2. Under the normal runtime mutation guard, validate the world is healthy and past complete initial publication; the Location and its anchor still resolve; the definition is compatible; the ID is unused; the bounded profile permits one creation; and the owner's revision can advance. Any repeated ID rejects without mutation, even with identical payload; this slice has no retry/idempotency protocol.
3. Prepare an immutable candidate record privately. Recheck the expected owner/spatial revision immediately before commit. Publish the one owner record and revision as a single mutation. Any expected rejection leaves record set, index and revision unchanged. The operation produces a deterministic result/receipt keyed to the input and committed boundary; it does not independently own the structure.
4. Reads enumerate structures in stable semantic-ID order. Cloning preserves identity, definition/revision, Location link and creation boundary; derived caches may rebuild. Whole-world validation rejects missing Location, duplicate ID, incompatible definition or creation predating the first simulated boundary.

The selected fixture supplies a predetermined semantic ID and submits at the runtime's current logical boundary. Within one boundary, the runtime's accepted operation sequence is the causal order; equal-boundary calls execute serially in that order. The first valid creation of the ID succeeds and any later call with that ID rejects, including an identical repeat. No allocator, retry protocol or independent construction clock is part of this slice. This is one authoritative owner and a spatial read/validation dependency, so no cross-store structural write transaction is needed.

## Material boundary

P14-A delivers one City, one exogenous source/item and aggregate market custody; it does **not** deliver a general construction-cost debit or atomic market-plus-structure commit. The inert proving structure at an arbitrary existing Location therefore has no material cost in P15-A. This is a scope statement, not a free-construction gameplay rule. A later material-cost consumer must choose source/title/custody, finite debit, insufficient-stock rejection and an all-or-nothing cross-authority commit against an applicable promoted P14 capability. Do not call `MarketRuntime.RemoveStockUpTo` and then create a structure: a partial removal or failed creation would violate the boundary.

## Dependencies, profile safety and validation

**Hard capabilities:** promoted P8-A Location/anchor authority and normal runtime mutation guard. P8-B/C City/site anchor is needed only if a future selected structure attaches to one of those owners; P14, P18, P20, P19 and P13 implementation are not P15-A prerequisites. This checkpoint introduces no runtime World Expansion.

The selected P12 `UnityBootstrap-Daily-v1` composition cannot silently acquire this new owner. The P15-A proving profile is explicitly separate; the daily profile's factory does not instantiate `StructureStore`. A composition/admission test must prove the daily profile excludes it. If an existing injection path can attach the store, admission must instead reject a populated unsupported store with a negative test, integrated serially with P12-B before domain promotion. The implementation worker may resolve that factual injection-path question from current code, but may not change the selected profile or permit silent omission. The owner exposes exact semantic state for future export, private staged hydration and pre-publication relationship validation, but P15-A implements no save DTO, loader or replay. Historical reconstruction must include the structure at and after its creation boundary, never before it.

Required focused validation: present/absent structure across boundaries T−1/T; missing/stale Location, duplicate ID, invalid definition, pre-publication or faulted runtime, revision overflow and rejected mutation with unchanged record/index/revision; deterministic ordering/clone; no spatial or presentation mirror; negative P12 profile admission/exclusion proof. Review the actual chosen operation/hotspot integration before implementation. No Unity test is run for this documentation candidate.

**Exclusions:** settlement founding, new City, population/government/territorial control, productive effect, generic catalog/crafting, material transfer, construction duration/workforce, shared activity, arbitrary world expansion, mod loader, save/replay implementation.
