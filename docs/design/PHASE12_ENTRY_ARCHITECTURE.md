**Status: UNAPPROVED proposal.** The code observations below use canonical baseline `1f4651e99db2c357dd3be3c6b9284d104379f706` (Phase 7). The current spatial dependency review also uses `docs/PHASE8_STATE.md` at `codex/phase8/canonical`, commit `ed7a40a86a6a16e9f4fda75703470c38135fda0e`; Phase 8-A through 8-C are now canonical there. The candidate slices below are discussion structure only; they are not checkpoint IDs and authorize no implementation.

## 1. Purpose and limits

Phase 12's stated continuation contract is: for a declared supported compatible version/profile, continuing from boundary T and saving at T, then loading and continuing with the same inputs, produces the same future authoritative results. Save is not replay or selective History. This inventory identifies candidate causal state, commitments, compatibility inputs, owners, and restoration dependencies that a later bounded technical design must cover.

The proposal follows `docs/SIMULATION_ARCHITECTURE.md` §§73–80, 85–86, and 91–93, especially the distinction between domain events, persistent history, diagnostic traces, World Truth snapshots, deterministic command inputs, save, replay, and History. It also follows `docs/EXECUTION_MODEL.md`'s reconstruction-sensitive gate. It does not establish event sourcing, a save format, a migration policy, a cross-host guarantee, or Phase 13's historical fork guarantee.

Phases 5–7 have formal closure records in their Phase States. Their delivered capabilities are not equivalent to persistence: Phase 7 explicitly defers save/load hydration and migration. Phase 12 is `ENTRY_ARCHITECTURE_READY`; no implementation checkpoint is schedulable from the Brief alone.

The current Phase 8 state adds canonical P8-A geography/terrain identity and revisions, P8-B passage authority, and P8-C City/Site anchors plus Person-level spatial presence. This inventory records those present-day dependencies, but does not silently extend the observed Phase 7 code baseline or claim that any save profile already supports them. P8-D remains ready for implementation and P8-E remains dependent on D at the cited Phase 8 state.

## 2. Accepted contracts and current limits

The following are inputs to later design, not choices made by this proposal:

- Save must preserve enough state to continue with the same future authoritative results under the same future inputs. An initial seed by itself is insufficient.
- The candidate payload must account for semantic IDs, the current absolute day and effective calendar, effective policy/parameter values, compatible definitions/content, authoritative truth, Knowledge, live plans/commitments, causal randomness, and ID/sequence allocators where future semantics depend on them.
- Persisted relationships resolve by semantic identity. Object references, Unity objects, registries, lookup indexes, and caches are not persistence identity and should be rebuilt when they are only indexes/projections.
- Runtime composition must retain one authoritative world. Diagnostics, events, and history do not become a second write authority or a universal mutation log.
- A save boundary should be a consistent point between ticks/transactions. The exact supported boundary and behavior for interrupted/faulted execution are not yet specified.
- Phase 7's documented Battle numeric profile is `unity-float32-current-host:v1` where supported. It does not promise arbitrary Unity-version, headless, cross-host, future `Simulation.Core`, or different-profile equivalence. It does not by itself prove that every domain's numeric behavior is portable.
- Phase 13's guarantee to reconstruct and independently fork every actually simulated boundary is explicitly outside Phase 12's closure claim.

## 3. Baseline code observations

### 3.1 World composition and mutation ownership

`SimulationRuntime` is the principal current composition boundary. It owns `SimulationTime`, an immutable runtime copy of `SimulationCalendar`, resolved `EffectiveSimulationConfiguration`, Person and domain stores, the NPC roster, optional systems, and a deterministic random-source reference. Its constructor validates and clones selected stores, wires cross-store dependencies, then binds supported mutable authorities to one `AuthoritativeMutationGuard`. That is a composition and mutation boundary, not a restore API.

Many current systems are optional constructor inputs, including travel, crime/justice, merchant trade, expeditions, directives, content, and randomness. The effective configuration and the set/version of executable providers therefore both affect behavior. A configuration name or service-presence flag alone cannot establish compatible future behavior.

The runtime's daily path increments `SimulationTime` before running ordered daily systems. The method is not a single all-domain transaction. Candidate capture must not take an in-flight view; a design must define a quiescent boundary and what happens when a tick throws or the runtime is faulted. Immediate world-command execution is a separate current boundary and is not yet an integrated queued-input protocol in `SimulationRuntime`.

### 3.2 No current persistence capability found

At this baseline, the scripts and EditMode tests contain no coordinated `SimulationRuntime` save/restore, hydration, stable save schema, or migration subsystem. Individual `[Serializable]` classes, Unity `[SerializeField]` fields, clone helpers, transaction rollback snapshots, and diagnostic snapshots are not such a capability. Several runtime objects contain non-serialized object references that must be resolved or rebuilt.

`WorldStateSnapshot` is an intentionally value-based diagnostic projection used by diff, invariant validation, canonical output, and digest. Its context covers many world domains, but it does not capture the full continuation envelope: effective configuration and provider composition, source content compatibility, random source/stream state, allocator high-water marks, complete future command payloads, or every active commitment. In particular, the current snapshot has no travel-party section. It must not be reused as a save DTO by assumption.

`WorldCommandService.Execute` applies a command immediately and records day, kind, origin, authority, result, affected/created IDs, event IDs, and diagnostic text. `WorldCommandRecord` does not retain the command payload; records alone are not a future input queue or a replayable command log. `RuntimeIdAllocator`, `WorldCommandIdAllocator`, and `SimulationRecordSequence` have private in-memory sequence state. A continuation design must decide which sequences and pending external inputs are part of its contract.

Existing tests cover domain transitions, composition, mutation boundaries, and diagnostic projections (including `SimulationRuntimeOrchestrationTests`, command tests, and `WorldStateDiagnostics` tests). The inspected test tree did not contain a save/load continuation suite. No tests were run for this documentation-only task.

## 5. Restoration dependency outline

Restoration needs to construct one consistent object graph, then expose normal validated mutation paths. This is a candidate ordering for technical design; it is not a prescribed format or final implementation order.

1. **Compatibility envelope first:** validate schema version, simulation/build and numeric profile identity, content/rule catalog compatibility, effective configuration, and calendar semantics before mutating any live runtime.
2. **Immutable definitions and base identities:** resolve the approved content catalog/profile; stage semantic IDs and existing runtime IDs; validate uniqueness and all cross-reference targets. Do not allocate replacement IDs for persisted entities.
3. **Time and factual foundations:** construct `SimulationTime` and calendar; stage world geography/topology, cities, markets/economic accounts, Persons/populations, and materialized NPCs. Link Person, city, location, item, and definition references by ID.
4. **Domain relation/store graph:** restore Person/genealogy and residence relations; spatial/content/site stores; institutions/offices/property/estates/political relations and Knowledge; armed forces/manpower/positions; then Conflict, War, and Battle relations. The exact order must follow current constructors and validation dependencies, not this prose order alone.
5. **Continuation commitments and inputs:** restore in-flight travel and parties, expeditions, NPC and merchant plans, scheduled directives, and supported pending external commands. Check that reciprocal bindings and remaining progress agree with their referenced NPCs/stores.
6. **Causal metadata and systems:** restore/derive relevant revisions and allocator high-water marks; recreate random-source implementation/state; recompose only a compatible provider/system set; rebuild registries, caches, and indexes from authoritative values.
7. **Validate then publish:** validate invariants and references on a staged runtime before it becomes usable. The design must decide whether publication is atomic by constructing a new runtime or by another explicit boundary. A partially hydrated or silently repaired world must not become a second authority.

Hydration paths must preserve existing authority boundaries: direct field injection is not a substitute for domain-owned constructors/transitions, and public mutation APIs must continue to revalidate current truth. Some current runtime constructor paths clone stores and `TryBindMutationGuard` disallows reuse across worlds; a save design needs a deliberate hydration path rather than relying on arbitrary input-store reuse.

## 7. Exact unresolved gates

### Architecture gates before full technical design

1. **Supported save scope:** Which runtime compositions/features are covered at initial delivery (Person/population, economy, travel, Knowledge, crime/social appraisal, politics, military, local content, optional services, legacy local stores)? Name supported and explicitly unsupported combinations. A partial scope must not be described as full-world continuation.
2. **Consistent boundary:** Does T mean only a successfully completed `AdvanceDay` return, also a completed synchronous command/transaction at the current day, or another boundary? Define concurrent mutation rules, exceptions/faults, re-entrant calls, pending commands, and save rejection while work is active. Existing day advance is not one global transaction.
3. **Numeric execution profile:** Which concrete supported profile(s) cover the entire selected scope, not only Phase 7 Battle arithmetic? Preserve the documented current limit (`unity-float32-current-host:v1` where supported) unless an approved contract expands it. Identify required code/runtime/backend/architecture or policy version tokens and the response to mismatch.
4. **Compatibility identity:** Define what must match for simulation code, schema, effective configuration, calendar, content definitions/rules, and composed providers. Decide which values are embedded, content-addressed, revisioned, or resolved by immutable catalog identity. Names/preset references alone are not enough.
5. **Restore behavior and safety:** Define dependency order, invariant checks, transaction/staging strategy, failure behavior, treatment of missing or changed references, and how mutation guards/revisions/allocators are restored. Do not repair missing world facts silently.
6. **Causal metadata classification:** For each included store, decide whether its revision, history, event/record counter, provenance, and past command summary affects future authoritative results, user-visible continuation, or neither. Persist only according to that explicit contract; do not infer a universal journal.
7. **RNG/provider contract:** Enumerate supported `IAuthoritativeRandomSource` implementations, demographic/manpower providers, action/content providers, and domain policies. State how a stateful or externally supplied provider is captured, pinned, or excluded.

### Product gates requiring user intent when guarantees expand

1. **Compatibility promise:** Which old saves, if any, must load across simulation releases? Is support same-build only, selected backward-compatible upgrades, or something broader? What should the user experience when a save is incompatible?
2. **Host and runtime promise:** Is continuation promised only on the originating host/profile, or across named hosts, Unity versions, headless execution, or future runtime implementations? Current architecture does not grant those broader guarantees.
3. **Content/mod promise:** May a save load only with the exact original content set, or with explicitly versioned compatible updates? How should missing, renamed, or behavior-changed content be handled?
4. **Retention expectations:** Which events, decision records, Chronicle/history, or other user-facing records should remain available after load? This is a save-product requirement distinct from causal closure and must not imply event sourcing.

Do not start a full technical design until the architecture gates above are answered within accepted semantics. Ask for product intent only if the desired promise is broader or different from the already accepted Phase 12 contract.
