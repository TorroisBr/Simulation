## 1. Purpose and boundary

P12-D supplies immutable factual-root and relation sections for the accepted `UnityBootstrap-Daily-v1` profile. It captures and reconstructs the already composed City, NPC, Person/population, genealogy, legacy spatial-network, and exploration-site truth. It does not define a new profile or add gameplay behavior.

The profile's existing P9-B genesis evidence and P8-A Hex/Location/scale facts are P12-C-owned roots. D references their stable identities where required but does not export, recreate, or infer them. P9-B outputs are historical facts: D hydration does not rerun bootstrap/genesis.

P12-D includes the legacy `SpatialNetworkRuntime` locations/routes and `ExplorableSiteStore` site identities/legacy location links used by the selected bootstrap. They remain distinct from canonical P8 spatial authorities. P8-B passage; P8-C City/Site anchors and Person positions; P8-D route plans/Knowledge; P8-E travel; P10 Ruin/LocalTopology; P14 source/material-flow state; P18 temporal state; P19 module/loader state; P20 shared activities; P13 reconstruction/fork history; external WorldCommand queues; `PlaceContentStore`; and optional systems absent from the selected composition are excluded sections. The profile admission layer must require these authorities to be empty or reject a populated excluded authority. Legacy route facts never substitute for P8 identity or canonical routes.

No Sleep, Dreams, robbery/gang, ritual, War gameplay, MegaEvento, procedural terrain, settlement, population, or backstory generation is introduced here.

## 2. Owner boundary and section assignment

Exports are immutable value projections produced by the authority that owns each fact. The future adapter may split a concrete owner's values across semantic checkpoint sections, but it must capture that concrete owner once, at one owner revision, and merge the disjoint projections before constructing/hydrating that owner once. It must not create a second source of truth or duplicate a field across sections.

| Concrete authority | P12-D-owned values | Cross-checkpoint split and single-owner rule |
|---|---|---|

Any E-owned provider state nested in the same concrete owner is a disjoint projection of the same single detached snapshot and owner revision/token. Merge D/E projections and hydrate the owner once; never recreate D root facts in E. |

The terms “owner revision” and “owner snapshot” above require implementation APIs. Current public enumerations, diagnostic projections, runtime clones, and rollback snapshots are not substitutes. P12-B's completed-boundary/capture token governs eligibility and stale-capture invalidation across supported mutation paths. The owner-specific revision is captured once and compared at the merge/hydration boundary; the existing `SettlementPopulationRuntime.Revision` is included as a subordinate semantic value inside the City owner record, not treated as a second City snapshot revision.

## 3. Immutable export contract

Each included concrete owner must expose a read-only export operation callable only under the P12-B capture token and owner-serialization window. It returns a detached immutable value graph (or immutable records plus private immutable collections), with stable typed identities and no live Unity/runtime object references. The export reports the same concrete-owner revision used by the merged D/E or D/E/F projections. Enumeration order is explicit and stable; it is preserved if a current consumer can use order as a causal/tie-breaking input.

The exported semantic records should contain only owner facts:

* City factual root: City runtime ID, City definition ID, legacy location runtime ID, population aggregate value and population revision. Economy data is supplied by the E projection of the same City snapshot.
* NPC core: `NpcRuntimeId`, definition ID, assigned D factual fields including exact `hiddenDaysRemaining`, and typed references to City/location/other D roots. Person binding is represented through the Person-owned reciprocal `PersonId`↔`NpcRuntimeId` relation, not a copied identity field with separate authority.
* Person: `PersonId`, optional birth/death absolute day, optional residence settlement runtime ID, and optional materialized NPC runtime ID. Preserve Person rows whether materialized or dormant.
* Genealogy: exact parent/child `PersonId` edges from the relation store.
* Legacy spatial: location ID records and route records `(routeRuntimeId, originLocationRuntimeId, destinationLocationRuntimeId, travelDays)`; preserve record order and parallel routes. A legacy route's travel days are the runtime's normalized value (at least one), not an independently recomputed duration.
* Site: site runtime ID, site definition ID and exact legacy location runtime ID. Exploration observations and spatial Knowledge are not site fields; they remain NpcRuntime-owned F values in the single D/F NpcRuntime projection.

The export must be detached: subsequent mutation of the source runtime or an array/list used in an export cannot mutate the captured record graph. It must not export derived reverse indexes (`outgoingRoutes`, Person materialization lookup maps, site-by-location query results, or `ImportantNpcs`) as independent truth. Rebuild indexes from validated primary records only where their owning API defines them as derived; otherwise preserve the owner’s authoritative list/order.

## 4. Staged hydration and dependency order

Hydration runs only into an unpublished private composition. No live runtime is partially overwritten. Owner constructors/factories used for hydration are internal, exact-value paths; ordinary gameplay mutation APIs and bootstrap generators are not used to recreate the saved facts.

1. **Admit and acquire roots (B/C).** P12-B validates the profile, completed boundary, compatible build/content/providers, owner-thread/quiescence, mutation health, and exclusion emptiness. P12-C restores exact typed ID allocator/registry and record-sequence state, deterministic-random continuation roots, the P9-B manifest/provenance, and the selected P8-A Hex/Location/scale facts. D consumes these roots and must not allocate replacement IDs.
2. **Restore legacy spatial locations.** Create exact legacy `SpatialLocationRuntime` objects from stable IDs, register each with the staged `RuntimeIdentityRegistry`/`SpatialNetworkRuntime`, and reject any identity collision. These are legacy locations, not P8 `LocationId` facts.
3. **Restore City owners from merged projections.** Resolve each City definition and legacy location reference. Merge the D root projection with any distinct E provider-state projection for the same single captured CityRuntime revision, validate no overlap and exact revision agreement, then construct one staged CityRuntime with the merged exact D roots and any distinct E provider facts. Do not create a partial D City and then independently replace it with E.
4. **Restore Person and NPC owners from merged projections.** Restore NPC core dependencies after Cities and legacy locations. Merge D/E/F projections for each `NpcRuntime` from the same captured owner revision, ensure each field has one semantic owner, and construct each NPC once. Restore `hiddenDaysRemaining` as the exact captured D-owned value through the exact-value hydration path; do not call `HideForDays`, whose gameplay duration semantics include the current day. Restore Person rows with exact PersonIds, dates and Person-level residences, then establish reciprocal materialization bindings only after all NPC identities exist. The staged `PersonStore` rebuilds its derived materialization index from validated pairs. Person residence stays attached to the Person even while a Person is materialized; NPC-only actors may retain their existing NPC-level residence semantics if that is the live owner contract.
5. **Restore population aggregate without transitions.** The City owner hydration installs its captured aggregate value and population revision; it does not replay births, deaths, migrations, or materializations. Validate represented-resident diagnostics against the current domain rule without silently “correcting” the aggregate. Any mismatch rejects the stage for diagnosis.
6. **Restore genealogy after Persons.** Hydrate exact relation records only after both Person endpoints exist. Reject duplicate, self, dangling or cyclic relations. Do not synthesize missing Persons or rewrite relations from NPC state.
7. **Restore routes and sites.** Create exact route objects after both endpoint locations are registered; register them in captured order so derived outgoing-route lists have the same order. Restore each site after its exact referenced legacy location and definition are available. Rebuild only owner-derived indexes. Never regenerate a route/site, infer an endpoint, or re-anchor a site through P8 geography.
8. **Validate and hand off.** The D stage returns a private validated owner package to P12-G. G composes it with every other included B–F package, runs whole-graph validation and parity/rejection gates, binds the fresh mutation guard, and performs the profile's single publication. D does not publish a runtime or claim atomic whole-profile replacement by itself.

## 5. Identity, relation, cardinality, and revision rules

* Preserve type distinctions: `NpcRuntimeId` identifies a simulated NPC runtime; `PersonId` identifies a Person across dormant/materialized/dead states; legacy spatial runtime IDs identify legacy locations/routes/sites; P8 Hex/Location IDs are separate P12-C identities. Never derive one ID from another or replace it on restore.
* Require nonempty exact IDs and uniqueness within each owning typed identity domain. The restored P12-C identity registry enforces uniqueness only among generated runtime-ID kinds registered with it; it does not merge `PersonId`, `HexId`, `LocationId`, and runtime-ID namespaces. Duplicate IDs in an applicable owner domain, incompatible definition references, or allocator state unable to continue without collision reject the stage.
* A Person may exist with no `NpcRuntime`. A Person's optional materialized NPC link must be reciprocal and one-to-one; an NPC not linked from a Person remains NPC-only. No Person can bind two NPCs and no NPC can materialize two Persons.
* For a materialized Person-backed NPC, residence truth is Person-level. NPC field projections must not duplicate or override that value. The referenced settlement must exist. Birth/death dates preserve exact nullable absolute-day values and valid ordering. Age and maturity are derived.
* Genealogy edges use `PersonId`, with both endpoints present in PersonStore. Reject self-parentage, duplicate edge, cycle, and dangling endpoint; do not apply extra domain rules not already required by the existing genealogy owner.
* Preserve each City aggregate and population revision exactly. Population is not recomputed from represented NPCs during hydration; validation uses the existing population semantics and reports mismatch as failure. Materializing/dematerializing NPCs does not adjust aggregate population.
* Every route has a unique stable runtime ID and registered, distinct origin/destination locations. Multiple route IDs may connect the same pair; this is not a duplicate. Preserve exact stored travel days and route iteration order. A route with an absent endpoint rejects.
* Every site has a unique runtime ID, compatible definition ID and an existing legacy location reference. Multiple sites may share one location. No universal one-to-one site/location or City/location cardinality is introduced.
* A site/location or NPC/City/location reference is serialized by its authoritative owner and checked in the merged stage. No dangling or silently nulled reference is accepted.
* Capture one revision per concrete CityRuntime and one per concrete NpcRuntime. D/E City sections and D/E/F NPC sections must have identical owner revision and snapshot token. A split, repeated or stale capture rejects before export acceptance. Preserve nested owner revisions such as settlement population revision within its single City snapshot. Other stores must expose owner revisions or be covered by the P12-B owner-operation generation; no guessed revision is added to existing semantics.

## 6. Validation and test contract

Implementation tests should establish owner semantics, not just DTO shape:

1. **Detached export and stable repeat:** capture empty and populated owners, mutate the source, and prove the exported values remain unchanged; repeated capture at one unchanged revision has stable content/order. Attempted D/E City or D/E/F NPC merges with different revision/token or overlapping field ownership fail.
2. **City roots and E merge:** round-trip City identity/definition/location, aggregate and population revision with any disjoint E-owned provider-state projection; assert one CityRuntime reconstruction and no production/consumption/repricing is executed during hydration.
3. **Person/population semantics:** cover unmaterialized Person, materialized Person-backed NPC, NPC-only actor, known/unknown birth and death dates, Person-level residence, population after materialization, and a City with aggregate population greater than named residents. Verify no age field is serialized and no hydration/materialization changes aggregate or population revision.
4. **NPC hidden-day state:** round-trip NPCs with both zero and positive `hiddenDaysRemaining`, and compare the value and subsequent `AdvanceHiddenDay` behavior after identical later daily inputs. Hydration preserves the current counter exactly; it does not replay `HideForDays` or consume a hidden day during restoration. Reject a malformed negative counter before stage acceptance.
5. **Genealogy:** round-trip a multi-generation relation graph and empty graph. Reject dangling endpoints, duplicate edges, self-edge, and a cycle before stage acceptance. Confirm serialized records are edge-owned and no Person/NPC row gains parent or child collections.
6. **Legacy spatial graph:** round-trip empty graph, multiple locations, parallel routes with distinct IDs, and different durations for the same endpoints while preserving route order/outgoing lookup. Reject duplicate location/route IDs, cross-kind collision, absent endpoint, self-route, and malformed identity before publication. Do not collapse parallel routes.
7. **Exploration sites/links:** round-trip zero and multiple sites sharing one legacy location; reject duplicate site ID, absent location, and incompatible definition. Preserve site identity, definition and legacy location binding exactly; ensure no P8-C anchor, P8 Location or P10 LocalTopology is synthesized. Verify exploration observation records and spatial Knowledge remain in the NpcRuntime-owned F projection and are not duplicated in site exports.
8. **Cross-owner consistency:** deliberately mismatch a Person residence settlement, NPC materialization reciprocal link, City location, site location, E City revision, or F NPC revision and prove the private stage rejects without publishing. Verify indexes are rebuilt from primary owner records and excluded populated owners cause profile admission failure.
9. **Continuation parity belongs to G:** after a complete B–F/G implementation, compare the uninterrupted and restored worlds under identical subsequent inputs. D's unit tests alone do not prove full save/load or daily continuation.

Required rejection cases must fail before publication and preserve the active runtime unchanged. Diagnostic snapshots/digests are comparison aids only after their field coverage is audited; they are neither the export nor hydration contract.

## 7. Owner implementation seams and hotspots

Likely D owner seams are `CityRuntime.cs` plus its population ledger; `NpcRuntime.cs`; `Person/PersonStore.cs` and `Person/PersonRuntime.cs`; `Genealogy/GenealogyStore.cs`; `SpatialRuntime.cs` with identity registry integration; and `ExplorableSiteRuntime.cs`/`ExplorableSiteStore.cs`. `SimulationRuntime.cs`, `TesteSimulacao.cs`, mutation lifecycle, P12 envelope/admission, and the daily loop are shared hotspots governed by B/C/G and the separate P18-D serialized-ownership work.

P12-E has an accepted adjacent owner boundary. Coordinate D implementation with E before coding: CityRuntime is one concrete City owner spanning D and E, captured once at one revision with disjoint factual and economy/provider projections merged before one reconstruction. NpcRuntime is one concrete NPC owner spanning D/E/F, captured once at one revision with disjoint section projections merged before one reconstruction. No two workers may independently add serializers, revisions, constructors, or hydrators to either class. If D/E work is parallelized, assign each worker disjoint files and a stable interface; integrate the shared-owner adapter serially in an integration branch.

P12-B is promoted within its bounded lifecycle and invalidation contract. D uses its completed-boundary token and serialized owner window; it adds no competing capture lock or invalidation mechanism. Each D owner still needs a detached exact export, a stable owner-issued snapshot/revision, and a private exact-value hydration path. A census witness or rollback snapshot is not a save adapter.
