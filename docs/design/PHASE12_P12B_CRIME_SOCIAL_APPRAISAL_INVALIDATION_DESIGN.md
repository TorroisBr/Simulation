## Contract and current evidence

The selected `UnityBootstrap-Daily-v1` runtime composes exactly one `CrimeSocialAppraisalWorldState` under `SimulationRuntime`. It owns one exact `TheftOutcomeStore`, `CrimeKnowledgeStore`, and `SocialReactionStore`, plus their existing `CrimeSocialAppraisalIntegration`. The child stores share the same `PersonStore` and `SimulationTime`. The authored sample profile begins with no Persons and its legacy NPCs have no `PersonId`, but that baseline is not immutable: current `SimulationRuntime.TryRegisterPerson` can register a Person after publication through the existing P12 membership/lifecycle path. Therefore a permanent explicit-empty fence would not safely cover all admitted P12 state transitions.

The stores expose direct result-bearing mutations. `CrimeSystem.TryExecuteSteal` uses the integration as its theft sink: it validates Person identity and calls `CanAcceptTheftOutcome` before transferring money, then calls `TryAcceptTheftOutcome`; if that write fails, existing code attempts a monetary compensation. The integration adds a TheftOutcome, then CrimeKnowledge and derived SocialReactions, and rolls back earlier store changes if a later step fails. `TryRecordKnowledgeAndAppraise` is another composite writer. The stores currently have no local census revision or P12 owner/epoch hook. Their standalone/runtime fault guards remain separate from P12 invalidation.

## Bounded P12-B contract

Track three exact singleton owner sections, each bound by reference to its child store under the one admitted `CrimeSocialAppraisalWorldState`:

- `p12.crime-social-appraisal.outcomes`: `TheftOutcomeStore`; rows keyed by the existing stable `TheftOutcomeId` from perpetrator, victim, absolute day, and stable occurrence key.
- `p12.crime-social-appraisal.knowledge`: `CrimeKnowledgeStore`; current rows keyed by evaluator `PersonId` plus `TheftOutcomeId`, with existing observation ordering/replacement semantics.
- `p12.crime-social-appraisal.reactions`: `SocialReactionStore`; historical reaction rows keyed by existing `SocialReactionId`, retaining source, target, and supersession links.

Each provider reports exactly one owner, current row count, and a monotone store-local revision. Identity and ordering remain the existing domain contract; no new ID allocator, random input, or temporal precision is introduced. Every successful row commit, replacement, or successful compensation advances that store's local revision. For a direct store call, the exact owner section is notified immediately after the commit. During a synchronous composite integration call, child callbacks advance local revisions and collect the changed section IDs; the outermost call notifies those sections once when the logical operation finishes. This matches the existing protocol contract: one outer commit may report multiple changed sections and advances the shared mutation epoch exactly once. `TryAcceptTheftOutcome` owns the outer context and reservation across its nested `TryRecordKnowledgeAndAppraise` call and any outcome compensation. That nested method joins the same context for the same integration instance and owner thread; it neither reserves nor completes a second token. A standalone `TryRecordKnowledgeAndAppraise` owns its own context. A rejected/no-op write that changes no stored row does not notify. Revision overflow and the single shared-epoch capacity required by the direct or outer composite logical commit fail before its first affected write.

Bind owner mutation callbacks to every direct store mutation and to the existing composite integration. A direct single-store commit preflights its exact owner section and local-revision capacity. It then selects one of the existing epoch paths before mutation: use the reserved-token path when `TryReserveMutationEpochCapacity` succeeds; if that call reports `OperationInProgress`, fall back only when `TryValidateMutationEpochCapacity` succeeds, which proves there is no active reservation and one immediate epoch increment is available. The fallback supports post-publication direct calls outside exactly one registered operation, because the public `NotifyCommittedMutations` path is owner-thread-bound but does not require an active operation. After the synchronous commit, report immediately with `TryNotifyReservedCommittedMutations` when holding a token, or `NotifyCommittedMutations` in immediate mode. If both preflights fail, reject before the owner write. Each composite operation preflights each possible owner section, reserves each store's local-revision headroom for its maximum successful writes and compensations, and selects the same reserved or immediate epoch mode exactly once before its first child-store mutation. The actual call graph bounds a full theft acceptance to at most two committed local-revision advances for Outcomes (add/remove), two for Knowledge (write/restore-or-remove), and four for Reactions (two appends/two removals). Knowledge-and-appraise without a new outcome needs at most two local-revision advances for Knowledge and four for Reactions. These are local revision capacities, not epoch counts. Nested store callbacks consume the active composite context by advancing the exact store revision and adding its section ID to the changed-section set; they do not notify or select another epoch path. At outer-scope completion, notify the set of all changed sections once with the selected reserved-token or immediate API, advancing the shared epoch once for the logical commit. If no row changed, release any token; immediate mode has no reservation to release. If forward writes are compensated, their local revisions still advance; a non-empty changed-section set is notified even when the final semantic rows equal their initial values, so the shared epoch invalidates prior reads. No reservation capacity is held across an unrelated owner callback.

On partial failure, preserve the existing compensation order and return values. Every committed forward or compensating row change advances its store-local revision; the outer logical operation reports all changed sections with one reserved epoch increment, even when final semantic rows equal the starting rows. Local-revision exhaustion must be detected before the first composite write so a later compensation cannot fail at revision saturation. Shared-epoch exhaustion must likewise be detected before the first composite write. No callback may be delayed past an unrelated owner write. All scopes remain synchronous and exact-store-bound.

For the theft action, the existing `CanAcceptTheftOutcome` semantic check remains before the account transfer. P12 capacity is reserved when `TryAcceptTheftOutcome` starts after the transfer; if reservation fails before any CrimeSocialAppraisal write, the existing CrimeSystem compensation path restores money. Do not hold a CrimeSocialAppraisal reservation across `EconomyTransactionService` or other owner callbacks. Preserve standalone behavior when the stores are not bound to the selected P12 protocol.

## Implementation seams

1. Add stable schema-v1 census providers for the three existing store references and register/bind them as part of the selected-profile runtime protocol before publication. Admission requires one exact child store of each kind and a readable baseline; the accepted SampleScene starts each count at zero.
2. Add monotone local revisions to the three stores and pre-mutation callbacks for every successful public write plus internal compensation writes. Bind the callbacks only once to the exact P12 runtime; retain existing runtime fault guards.
3. Add one narrowly scoped composite mutation context to the existing integration. The outer `TryAcceptTheftOutcome` context preflights local revision headroom for its complete bounded call graph, including nested `TryRecordKnowledgeAndAppraise` and any outcome rollback (2/2/4 advances for Outcomes/Knowledge/Reactions), all three owner baselines, and one shared-epoch increment before its first child-store write. Select epoch mode once: retain the existing reservation if `TryReserveMutationEpochCapacity` succeeds; if it returns `OperationInProgress`, use immediate mode only if `TryValidateMutationEpochCapacity` succeeds; otherwise reject before writing. Immediate mode is permitted because this exact synchronous bridge runs on the bound owner thread, rejects unrelated/reentrant callbacks while active, and notifies before returning; the existing immediate protocol API does not require a registered operation. The nested `TryRecordKnowledgeAndAppraise` detects that exact same-thread integration context, joins it, and may consume only the Knowledge/Reaction local headroom already budgeted by the outer theft operation; it does not select another epoch mode, notify, release, or complete the token. The outer context remains active through any outcome compensation and alone closes/notifies. A standalone `TryRecordKnowledgeAndAppraise` creates and owns a context, preflighting local headroom for its complete call graph (0/2/4 advances for Outcomes/Knowledge/Reactions), relevant baselines, and one shared-epoch increment using the same mode selection. Each successful child commit/compensation advances its local revision and records the exact section ID in the active context without notifying. On outer close, call `TryNotifyReservedCommittedMutations` once with the distinct changed section IDs if a token was acquired, or `NotifyCommittedMutations` once in immediate mode; if there were no row changes, release a token only when present. A nested scope may only join this specific declared call-graph edge; reject other reentrant composite entry before it writes. Direct store APIs use the existing one-write preflight/notify path unless they are a child call already admitted under this exact outer context. This uses the current token and immediate APIs with their existing one-epoch-per-outer-commit semantics; it does not add operation IDs, a capacity-N reservation API, or a general transaction framework.
4. Bind the exact `CrimeSocialAppraisalWorldState` in `SimulationRuntime` and verify each registered provider points to its current child store. Do not add a separate runtime instance or alter bootstrap content.
5. Keep `CrimeSystem`'s existing money-before-appraisal order and compensation behavior. The P12 hook must not change robbery eligibility, money amounts, witness/knowledge rules, appraisal outcomes, reaction identity, or standalone unbound behavior.
