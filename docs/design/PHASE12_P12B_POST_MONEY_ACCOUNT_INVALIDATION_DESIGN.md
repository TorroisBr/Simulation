# P12-B owner-commit invalidation design refresh

**Status:** Bounded technical design candidate; base P12 canonical f913dd088f71b74cfab7c1bd8a1a79b7ce9a29ea. This refines the already accepted P12-B design against the post-Market/MoneyAccount owner and operation matrix. It adds no Phase/checkpoint ID, product behavior, architecture semantics, or implementation authorization beyond the previously accepted P12-B–P12-G prerequisite scopes.

## Purpose and boundary

The selected UnityBootstrap-Daily-v1 profile has owner-local census witnesses for more authorities after the Market and MoneyAccount promotions, but no complete shared commit epoch for supported writes. The promoted MoneyAccount family covers one account owner per rostered NPC only. It does not cover PopulationEconomyRuntime or account-backed MarketCounterpartyRuntime owners, and a passive account witness does not observe commits. The existing ContinuationCensusProtocol already provides:

- versioned required-section contracts and owner-backed census witnesses;
- a partial owner-thread binding and caller-registered active-operation accounting;
- a monotonically increasing mutation epoch;
- NotifyCommittedMutation(s), which validates changed section IDs against registered owner identity/revision evidence and advances the partial epoch;
- roster reconciliation for the currently registered PersonStore and dynamic NPC families.

The design uses that coordinator and those owner APIs. It does not introduce a generic observer/event bus, lock manager, rollback framework, new save schema, or second source of world truth. Authoritative writes retain their owning domain's success/failure semantics.

## Required evidence boundary

A P12 profile can be eligible only when its immutable manifest identifies the exact supported bootstrap/build/runtime/configuration/content/provider composition and complete owner section set. Each section must specify stable section identity, schema, role, concrete owner identity, exact cardinality including explicit zero, and owner-local revision. Passive providers alone do not become protocol coverage until registered in this manifest.

The accepted daily profile excludes P10 topology, P14 flow, P18 temporal state, P19 extension state, P20 activities, P13 fork guarantees and external WorldCommand queues. Composed owners that are known empty still require an owner-issued exact-zero witness. The selected `Simulation-GeneralTest` City assets use the `CityData` defaults `MarketLiquidityMode.Open` and `ConsumptionPaymentMode.Free`, so their `MarketCounterpartyRuntime` and `PopulationEconomyRuntime` expose no `MoneyAccountRuntime`; this conditional account family is not composed by this profile. Preserve the selected asset/config identities in the profile manifest so an account-backed change cannot silently reuse this zero-owner contract. P18 keyed-sale receipts remain an exact-zero conditional section for this legacy profile; the P18-D consumer is not imported into the P12 daily path.

`MoneyAccountRuntime` has two internal prepared-install overloads. Current call sites are `EconomyTransactionService.TryExecuteKeyedMarketSale` and `CityRuntime.TryCommitDailyEconomy`; the former is the P18-D keyed-sale consumer and the latter commits a P18 timeline-owned daily economy step. The selected P12 profile rejects P18 timeline composition and excludes P18-D, so these prepared installs are explicitly outside this P12 contract. They must not be presented as covered by the NPC MoneyAccount census or used to define its first adapter. The P12-relevant account writes are the successful `TryDebit`/`TryCredit` paths, including direct NPC wrappers, transaction transfers and successful compensations.

## Commit and operation rules

1. **Owner commit notification.** A domain owner reports a change only after its authoritative local install and local revision have committed. The notification names the exact registered section IDs that changed and carries the post-commit census/revision from those owner instances. Failed preflight and no-op do not notify. Local revision deltas without a notification do not advance the common epoch.

2. **Atomic prepared install.** If a domain operation stages one logical install across several owners and publishes it atomically, notify once after the install with the full changed-section set. Do not report staged/uncommitted values.

3. **Multi-step or compensating operation.** A supported outer operation scope begins before the first possible authoritative commit and remains active through success, failure handling, compensation, and result publication. Each committed owner change must be notified while the scope remains active. A successful compensation is itself a committed change and must be represented; a later failure cannot erase an already committed write from the epoch. P12-B does not add whole-operation rollback.

4. **Continuation bookkeeping failure after a domain commit.** It cannot convert a committed domain success into a false domain failure or imply rollback. The P12 admission/eligibility coordinator faults closed, the operation scope exits safely, and no capture token can be issued from the faulty runtime.

5. **Operation scope.** Register a stable operation contract before sealing the profile, enter/exit it around every supported synchronous multi-owner boundary, and reject capture while any registered scope is active. The existing active count is accounting only; it is not a lock, store synchronization, or thread-safety promise. Daily and bootstrap scopes remain as currently reviewed and bounded.

6. **Direct owner entrypoints.** A public writer that can mutate admitted state must either route through an owner-bound notification boundary or be excluded/rejected by profile admission. An outer service scope does not cover a bypassable child writer. Direct call paths that remain supported must be listed explicitly.

7. **Owner/revision drift.** Census assessment rechecks the same registered instance, cardinality, and local revision. Any unnotified revision change, owner replacement, missing owner, or unexpected section faults/blocks eligibility. A later assessment detecting drift is fail-closed detection, not proof that the common epoch was current during the write.

## Dependency-ordered implementation sequence

These are implementation slices within accepted P12-B and its already authorized prerequisite work, not new checkpoint IDs:

1. **Reconcile the owner inventory.** Finish the effective selected-profile and explicit-zero map before any eligibility claim. Reuse promoted providers and add no provider where exact identity/count/revision already exist. Distinguish actual composition from P18/P14/P10/P19/P20 exclusions and identify any selected owner not covered by the 142-section partial kernel. This full inventory is a dependency for eligibility; its incompleteness does not prevent a code slice over already registered owners.
2. **First coherent write slice: NPC-to-NPC trade.** Do not implement an isolated MoneyAccount callback first. Add the stable `runtime.economy.npc-trade` operation contract around `EconomyTransactionService.TryExecuteNpcTrade`, lasting from before its first possible commit through its compensations and returned result. Bind each exact rostered buyer/seller `MoneyAccountRuntime` and `InventoryRuntime` to the existing per-NPC sections. After each successful local install, notify the exact changed section while the outer operation remains active: buyer/seller account debit/credit, seller inventory removal, buyer inventory addition, and every successful account compensation. Failure before a commit and no-op do not notify; a later failed stage cannot erase earlier committed writes. This operation changes only the four registered NPC-owned sections. Direct account/Inventory APIs outside this service need their own single-owner notification boundary or must remain explicitly outside eligibility; the hook must not silently imply that other service-level transactions have an enclosing scope.
3. **Remaining selected economy transactions.** Add exact outer scopes and changed-owner notifications for the other P12-supported operations identified in the audit, including market purchase/sale, money transfer, population consumption where configured, travel charge/restore and group compensation, plus actual daily merchant call sites. Map Market, Inventory, City/account, merchant/transaction receipts, NPC plans and Commercial Knowledge where those paths commit. A service scope alone is insufficient if child owner writers bypass notification, and owner-local notifications alone do not account for a multi-step outer operation. P18 keyed-sale prepared installs/receipts stay excluded and exact-zero for this profile; P18 timeline `CityRuntime.TryCommitDailyEconomy` is also excluded.
4. **Remaining supported operation families.** Integrate lifecycle/population, travel/TravelParty, Expedition, Justice/Crime, directives/ActorChoice, political/military and spatial owners in isolated owner/hotspot slices. Each slice names owner sections, successful commit points, direct bypass closure, scope, compensation behavior and tests before wiring.
5. **Capture-eligibility lifecycle.** Only after the complete owner set and every supported mutation path are registered and independently validated, implement the accepted successful-boundary sequence/token rules. Recheck all witnesses after P12-G collection. Keep a missing owner or unsupported writer fail-closed; do not let partial protocol assessment advertise CaptureEligible.

The first implementable operation is deliberately the bounded NPC-to-NPC trade transaction, not an account-only adapter. Its exact account and Inventory identities/cardinalities/revisions already exist in the partial protocol; its success and compensation writes are visible in one service boundary. It can establish one useful operation slice while leaving P12-B incomplete. It does not cover MerchantSystem's subsequent plan completion, market-based transactions, City-owned accounts, or any other operation family, and it cannot make the partial census eligible for capture. Local Market census remains a separate owner witness, not an epoch substitute.

For the bounded integration seam, `SimulationRuntime.InitializeNpcRosterCensusProtocol` must register `runtime.economy.npc-trade` before `SealOperationInventory`, alongside the already selected-profile operations. `TesteSimulacao` constructs the shared `EconomyTransactionService` before `SimulationRuntime` and passes that same instance to `MerchantSystem`; after the runtime has initialized its protocol, bind that service to the runtime's internal P12 operation/notification bridge before bootstrap publication. The service then enters the named `SimulationOperationScope` at the start of `TryExecuteNpcTrade` and disposes it on every return path. It obtains the already-registered dynamic IDs from the bound NPC RuntimeIds: `p12e.npc-money-account/{RuntimeId}` and `p12f.inventory/{RuntimeId}`. After each successful debit, credit, remove, add, or compensation, it calls the existing protocol notification path for exactly that owner section; it does not combine sequential commits into a fictitious atomic install. With no P12 context (for example, isolated domain tests), the existing transaction behavior remains unchanged. If the bound P12 bookkeeping fails after a domain commit, the protocol faults closed and the service preserves the domain transaction's established result semantics.

This operation scope ends when `TryExecuteNpcTrade` returns. In the selected MerchantSystem path, subsequent merchant-plan completion remains a separate uncovered commit; it is intentionally not included in this first slice. Direct `MoneyAccountRuntime`/`InventoryRuntime` entrypoints and all other transaction methods likewise remain uncovered until their own writer mapping, notification path, and enclosing operation scope are completed or the profile contract explicitly excludes them. Therefore the NPC-trade slice is progress on P12-B, not evidence that any other account write, all account owners, the economy operation family, or the profile is capture-safe.

## Validation and review boundary

For each code slice, test successful commits, no-op and rejected operations, local revision drift, owner replacement, roster add/remove/reconciliation, wrong-thread attempts before mutation, nested day scope, and coordinator failure after an owner commit. Then run the required P12 focused suites, full EditMode, official Smoke and git diff --check; retain exact XML/log artifacts. Independent exact-tip implementation review and canonical promotion are separate gates.

The design candidate itself is documentation-only. It requires independent exact-tip design review and git diff --check; no Unity tests apply. The audit in PHASE12_POST_MONEY_ACCOUNT_BLOCKER_REFRESH.md is the current owner/operation evidence base.
