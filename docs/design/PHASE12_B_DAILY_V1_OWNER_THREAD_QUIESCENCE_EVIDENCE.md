# P12-B selected Daily-v1 owner-thread and quiescence evidence

**Audit base:** `5b8ba1c8e015180f3fa4bddaf0d301610c0e9e2d` (`codex/phase12/P12BDailyOwnerLedger`).
**Profile:** accepted `UnityBootstrap-Daily-v1` (`SampleScene` → `Simulation-DailyV1.asset`, P9-B-only).
**Purpose:** reconcile current implementation evidence for owner-thread admission and registered operation scopes against the retained effective-owner ledger and 23-operation matrix. This is a bounded source/test crosswalk, not an implementation checkpoint or completeness certificate.

## Contract and evidence boundary

The P12 Brief limits P12-B to exact profile/provider admission and capture eligibility at a successfully completed daily boundary. Its accepted capability decomposition and `PHASE12_B_TECHNICAL_DESIGN.md` already define the bounded requirements: bind the actual Unity `Start` thread, keep bootstrap publication and admitted synchronous operations in registered scopes, reject wrong-thread calls, and publish a runtime-bound boundary token only after successful completion. This note reports what the current source/tests establish about the first part of that contract.

`PHASE12_B_DAILY_V1_EFFECTIVE_OWNER_COMMIT_LEDGER.md` and `PHASE12_B_DAILY_V1_REGISTERED_OPERATION_MATRIX.md` are retained reviewed evidence. Their known 275-section inventory and 23-operation crosswalk are useful coverage inputs; neither certifies that all supported ingress is enumerated. The matrix below maps the currently identified supported ingress to owner-thread enforcement, scope and observed synchronous behavior. It does not elevate a sealed operation list into proof of global quiescence.

## Excluded or not established as supported ingress

| Surface | Current classification and limit |

| Public `ContinuationCensusProtocol` operation set | The sealed inventory rejects unregistered IDs and tracks only operations whose callers enter it. | P8-B/C/E mutators and P8-D observation/route-plan producers | Exact owner census or explicit-zero evidence does not establish a current selected Daily-v1 writer. | P10-A/B, P14-A/B, P16/P17 proving compositions; P18 timeline and receipt APIs | Conditional/out-of-profile for accepted Daily-v1. | External `WorldCommand` / ActorChoice UI queue and P12-F Expedition autonomy | The accepted Daily-v1 profile does not compose the external command queue; its reserved ActorChoice handler has no selected production caller. `ExpeditionStore` and `ExpeditionSystem` are constructed and exposed in Daily-v1, but Expedition autonomy is absent from its normal supported flow and remains deferred to P12-F dependencies. | Arbitrary Unity callbacks, future plug-ins, or code added after this audit | The observed pipeline callback runs synchronously, but this audit does not prove future/user-supplied callbacks cannot enqueue work. Any newly supported ingress or callback that can outlive its scope requires a fresh profile and scope review. |

## Remaining obligations

This evidence does **not** prove:

1. that the 23 registered operation IDs exhaust every supported Daily-v1 ingress or that all 275 census sections are complete over every reachable state;
2. that all owner reads/writes are serialized exclusively on the Unity owner thread, or that no callback can escape the listed synchronous scopes;
3. runtime-wide quiescence or general thread safety. The counter measures only operations that are registered and correctly entered;
4. complete shared-epoch coverage or a completed-boundary token tied to successful advance sequence;
5. capture eligibility, export, hydration, P12-A readiness, P13 readiness, or Phase 12 closure.

The smallest next evidence step is an independent exact-tip review of this matrix against the 275-section ledger, 23-operation matrix, selected bootstrap call graph and focused test inventory, with any uncovered in-profile caller recorded by exact source path. Do not add runtime wiring unless that review finds a concrete supported unscoped ingress. Once the supported-ingress/quiescence evidence is complete, the already-reviewed P12-B boundary lifecycle design can guide the separate Daily-v1 successful-advance sequence/token capability; it must remain fail-closed until owner census and committed-write invalidation prerequisites are complete.
