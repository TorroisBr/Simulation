# P16-A — One passage, one ArmedForce, finite carried supply

**Status:** candidate bounded checkpoint and technical-design boundary for independent review. **Architecture base:** `da34d50bd7831ac3eefab31e925492ede8dded5c`. **Product scope:** explicitly approved on 2026-10-03. No implementation or canonical promotion is authorized by this file.

## Proof and selected profile

One existing active `ArmedForceId` at a factual source Hex crosses one existing valid registered passage option to its neighboring destination Hex in one committed military operation. The force carries a finite quantity of one compatible supply item, authored as part of the proving world's initial truth. A successful crossing consumes a fixed positive quantity and changes the force's factual position. An insufficient quantity, closed/blocked passage, stale source, terminated force, invalid option or incompatible context rejects without changing position or supply. The operation has no duration, second clock, route plan, Person availability, Battle, War, occupation or territorial effect. A later timed military movement may consume P18 but cannot reinterpret this one-boundary operation as a route.

The current code has `ArmedForceStore` for force identity/lifecycle, `ArmedForceSpatialStateStore` for optional typed position, and P8's `SpatialAuthorityStore`/passage evaluation for factual adjacency, options and conditions. The legacy `OperationalLocationReference` is explicitly not factual physical position. P14-A supplies bounded finite item/stock semantics but no force-held supply, replenishment or logistics network. P16-A extends the **existing military position owner** with one-item carried supply in a single immutable per-force operational record; it does not create a second position or supply authority. Initial stock is authored before the first simulated boundary; no market transfer or exogenous runtime mint is implied. The supply item identity/content revision and positive fixed cost are effective compatible inputs. P14 title/custody distinctions remain intact; P16 owns force custody/consumption, not the P14 City market.

## Authority and atomic execution

`ArmedForceSpatialStateStore` remains the sole owner of current physical position and gains the bounded carried-supply state for this selected profile. Its internal per-force record is replaced atomically; the existing position query remains a read of that record. The implementation surface is `ArmedForceSpatialPosition.cs`, a military movement operation facade invoked through `SimulationRuntime`, the P16-A proving composition, and focused EditMode tests. Existing P7 initialization, query and clone behavior migrate to the expanded record without changing their public factual meaning. The proving profile binds one `ItemData.DefinitionId`, an effective profile/content revision, initial nonnegative quantity, and a fixed positive per-crossing debit. The military movement service coordinates passage validation but owns no position, stock mirror or second clock. The implementation boundary is:

1. Validate active force, exact current source Hex, registered adjacent endpoint Hexes, an explicit passage option, compatible military traversal context, current passage/barrier conditions, sufficient finite carried stock, positive cost, owner-thread/runtime guard, and owner revision/capacity. Use P8 passage evaluation for factual availability, not a civil TravelParty or civil effort as automatic military supply cost. `Impaired` is passable only when P8 evaluation says `IsAvailable`; the fixed v1 supply debit does not infer a cost from civil effort.
2. Prepare one replacement operational record privately. Bind it to expected force/owner/passage revisions and the operation's logical boundary/order; revalidate passage and expected revisions immediately before execution. All ordinary rejection paths occur before any live write.
3. Commit under one non-reentrant runtime operation/publication boundary by replacing that one per-force record and advancing the owner revision once. No public reader or subsequent causal work observes intermediate position/supply, and rejected operations leave both values and revision unchanged. A successful operation emits one deterministic outcome/receipt; the receipt is derived, not a second truth.
4. Restrict ordinary post-start force relocation to this military authority so callers cannot bypass finite supply through `TrySetPosition`. Preserve an explicit pre-publication initialization path for already supported P7 composition and tests; existing direct callers must migrate to it only when initializing World Truth. The movement operation has an explicit stable operation ID retained in the force owner's accepted-operation set for this bounded profile. An identical repeat rejects before mutation; no retry/idempotency protocol is implied. The accepted-operation set, position, quantity and revision clone together. Any P12-B mutation-invalidation hook is integrated serially at the existing runtime hotspot.

The selected proving operation may be a controlled simulation command with explicit operation ID and fixed supply cost; it need not introduce player command rules. If an external Actor/GM/editor input later invokes it in a durable world, payload, authority, logical boundary and accepted order must be retained. Same-boundary competing moves resolve by canonical operation order; the second sees the first's new source/supply and rejects if stale. No implicit retry or second movement occurs.

## Dependencies, profile safety and validation

**Hard capabilities:** P7 active ArmedForce and typed position, P8-A adjacent factual Hexes and P8-B registered/evaluable passage, plus P14-compatible item identity and finite material custody semantics. P14-A's City stock is not itself force supply; the bounded extension of the existing military owner and authored initial stock are part of P16-A's reviewed implementation scope. P18 is a compatibility constraint on logical boundary/order, not a scheduler dependency because this slice has no duration. P20, P19, P13 and full P12 are not prerequisites.

`UnityBootstrap-Daily-v1` currently has only one selected P8-A Hex and no P8-B passage; this P16-A proving composition must stay outside that profile. The existing `ArmedForceSpatialStateStore` is already in the P12 owner census, so adding carried supply to it is an admission-sensitive change even if a passage cannot be composed. Before domain promotion, a negative test must show the selected profile rejects non-default P16 supply/accepted-operation state unless that state is explicitly and completely admitted. Add the fail-closed inventory/admission hook if current P12-B composition requires it, integrated serially with active P12-B. Do not silently omit new state from a nominally supported owner. Retained state comprises force identity, exact position, supply item/quantity, initial provenance, passage/condition identity and effective revisions/context, logical boundary/order and any accepted external command. These form future exact export/staged-hydration/graph-validation seams; no P12 serialization is implemented here. Historical forks before the move retain source position/full supply, and at/after it retain destination/debited supply.

Required focused validation: successful one-hop movement and exact debit; insufficient stock; closed/blocked or changed passage, and impaired passage under its explicit availability rule; nonadjacent/unregistered endpoint; stale source/revision; terminated/missing force; duplicate operation; deterministic order of simultaneous commands; atomic unchanged position/supply/revision on every rejected path; no direct post-start bypass; clone/invariant checks; P12 exclusion/rejection proof; no Battle/War/control effect. Combined promotion needs current-base regression for P7 force, P8 passage and any affected P12-B guard/owner census. No Unity test is run for this documentation candidate.

**Exclusions:** route planning, multi-leg movement, duration, weather, scouting, replenishment/transport network, Person actor availability, civil TravelParty, P20 participation, automatic Battle/War/occupation/control, new geography or settlement, mod loader, save/replay implementation.
