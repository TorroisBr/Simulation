## Review findings

- **Source-use inventory and seed sufficiency:** `TesteSimulacao.InitializeSimulation` constructs the selected bootstrap's `DeterministicRandomSource` from the exact effective seed (`simulationConfig.simulationSeed` when fixed, otherwise zero), then supplies the same instance to `SimulationRuntime`, `CrimeSystem`, and `NpcDecisionSystem` (`TesteSimulacao.cs:214, 290-300, 1551-1559, 1579`). The included keyed draws are the NPC choice, action-success, and crime-target keys (`NpcDecisionSystem.cs:337`, `SimulationRuntime.cs:10781-10788`, `CrimeSystem.cs:999-1002`); each uses the default draw index zero. `DeterministicRandomSource` has immutable `Seed` and computes direct keyed values from seed, key, and draw index without a mutable provider cursor (`DeterministicRandom.cs:60-92`). Its `CreateStream` method creates a separate mutable `DeterministicRandomState` cursor (`:40-58, 94-99`); the production `SeededConflictRandomSource` use is in the separate WorldObserver demo (`ConflictFoundation.cs:674-690`, `WorldObserverDemoBootstrap.cs:161-165`), not the selected Daily-v1 bootstrap.
- **Other deterministic sampling boundaries:** the selected Daily-v1 profile keeps natural mortality and aggregate demography disabled under the accepted P12 profile contract; the runtime's daily demographic step therefore does not execute those sampler consumers. Any profile that enables them requires a fresh source-use/profile review. Battle resolution also has its own separately keyed authority and is not composed by this selected bootstrap. These exclusions do not omit a mutable cursor or seed used by the reviewed Daily-v1 root.
- **Identity and immutable snapshot:** the proposed snapshot carries schema, provider and algorithm identities/versions plus the exact `Int32` seed. All seed bit patterns are valid for the current provider. The get-only scalar DTO and owner `CaptureSnapshot`/private staged-factory boundary are appropriate. Staging rejects null or unsupported metadata without consuming a draw, mutating the active source, allocating identity, or creating a stream. `IAuthoritativeRandomSource` and consumer keys remain unchanged.
- **Algorithm/version and compatibility:** `fnv1a64-keyed-utf16` accurately identifies the current seed/key/draw mixing and folded output mapping, with an explicit algorithm version to advance when outputs can change. Exact provider/schema/algorithm checks support fail-closed reconstruction for the accepted same-build/current-host numeric profile. The design makes no unsupported cross-host or cross-version numeric portability promise, consistent with the accepted profile and architecture.
- **P9 provenance boundary:** P9 genesis owns the authored/effective seed provenance (`SimulationGenesisPipeline.cs:174-175, 720-721`); this DTO owns only the effective provider seed and does not duplicate manifest provenance. When P12-C later composes the staged RNG root with the P9 manifest, it must require the effective seed to agree with the manifest and reject disagreement. That cross-owner check is outside this bounded owner snapshot slice and is recorded as an integration constraint, not a design blocker.
- **Validation plan:** the proposed focused tests cover metadata/seed capture, exact seed round-trip, keyed output parity at zero and explicit nonzero indices, integer boundaries, malformed metadata, immutability/no-advance behavior, and normal Daily-v1 composition. Existing deterministic-random tests and the stated integration/full regression, Smoke, LongRun, and diff-check gates are appropriate for the later implementation candidate. No Unity tests were run for this design-only review; `git diff --check` passes for the candidate range.

No blocking product or architecture ambiguity remains. The reviewed design is suitable for implementation only within its listed Daily-v1 root snapshot scope. P12-C's P8-A geography and P9-B provenance owners, aggregate consistency validation, P12-A, P13, and Phase 12 closure remain separate obligations.
