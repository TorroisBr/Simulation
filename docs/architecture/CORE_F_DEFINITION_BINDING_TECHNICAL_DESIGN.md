### Frozen construction flow and API

Use the already-approved entry point `DailyV1Application.TryStart(DailyV1EffectiveDefinitions definitions, DailyV1ApplicationHost host)` (§11). Core genesis retains the graph on the candidate/session and resolves each configured string ID once through its existing typed map before creating any mutable owner. Constructors receive canonical definition nodes (or the same graph when they must resolve nested config IDs); no second DTO/value cache, graph rebuild, per-owner interning table, external resolver interface, or authoring `SimulationConfigData` argument is added. Values used for initial quantities/prices/configuration come from the current immutable graph's `Values` and existing effective/default conversion.

Required internal validation before `WorldId`, allocator or owner mutation:

- Every selected root/config ID resolves in the correct typed family map.
- Every nested item/action/status/job/location reference required by the selected Daily-v1 path resolves; wrong-family, missing or unbound references reject with the existing profile/persistence failure category.
- The exact `DailyV1*Definition` instance selected by the map is passed to every runtime row/slot. Duplicate rows and slots must not be “repaired” by equality on strings.
- The Unity adapter rejects a second distinct asset with duplicate `(type, DefinitionId)` before graph construction; same-asset aliases are allowed. Graph factory duplicate-ID checks remain for .NET fixture and any direct graph creation.
- A loaded P12 image resolves its stable IDs against the same application graph. Staged target factories receive those canonical nodes; failure is detached and leaves the old live session/slot untouched.

Apply the same graph parameter to the P12-D root staging entry points for City and NPC owner snapshots (and any other root snapshot factory that resolves these family IDs), reached from `P12DDailyV1OwnerPackage`'s detached stage path. Every decoded item/city/NPC/action/status/job/trait/attribute ID resolves from the application graph and is passed as the exact canonical node to its staged owner factory. Codecs continue emitting stable IDs; P12 staging cannot consult a Unity ScriptableObject index or construct another family map.

The graph's maps are family-specific; a City ID and Item ID may be equal without collision, while duplicate IDs within one family reject. Wire IDs remain the authored `DefinitionId` strings; do not add prefixes, reinterpret casing, or replace ID-based P12 rows with CLR object serialization.

## Unity conversion boundary and missing typed semantics

Keep `DailyV1DefinitionAdapter`, `SimulationConfigData`, ScriptableObject definitions, Unity serialization attributes, validation, lazy getters and authored-default conversion in Unity. Preserve the adapter's current prime/read order, effective configuration, calendar, list order, enum numeric value plus spelling, unknown-enum treatment, reference closure, selected-content projection and P9/P8/provider identities. Core accepts only the finished graph and consumes it; it must not duplicate Unity authoring conversion.

Unity destroyed-object handling must stay at the adapter edge: where a `ScriptableObject` is statically typed as `UnityEngine.Object`, use Unity's overloaded `asset == null` to reject fake-null/destroyed assets, and use CLR `ReferenceEquals` for same-asset alias/identity checks. Preserve the existing distinct-object duplicate identity rejection. Do not use Unity fake-null operators in Core.

The current graph carries some capability/trait values but lacks the typed contracts needed for real consumers. `DailyV1CapabilityAttributeValue` and `DailyV1CapabilityAttributeModifier` are string-ID/value records; `DailyV1NpcData.traits` is a list of IDs; `DailyV1ItemData.capabilityModifiers` carries attribute IDs. `DailyV1EffectiveDefinitions` has no Trait or CapabilityAttribute maps. `DailyV1DefinitionAdapter.IsSelectedAssetType` admits those ScriptableObject families, but `TryCreate` currently captures them only in selected content records and does not intern typed nodes. The concrete owner graph needs those references resolved to one canonical graph node when a supported consumer uses them.

Add typed identity nodes and maps to the same graph (not new public Store/mod surfaces). The adapter's existing `CaptureAssets` result already contains the exact admitted `TraitData` and `CapabilityAttributeData` assets, including assets reachable only through NPC traits, capability values, item modifiers or optional configuration inputs. Extend the adapter conversion pass to collect deterministic `{id, displayName}` values; derive display names through the authoring fallback (blank name → ID), reject blank IDs through each source type's existing `TryValidate`, and pass those values to `CreateSelectedSchema`. Freeze one same-graph Trait map and one CapabilityAttribute map by `DefinitionId`, rejecting same-family duplicates like the six current maps. These are graph nodes, not a second value cache:

Exact implementation shape: add `public sealed class DailyV1TraitDefinition : DailyV1DefinitionRecord` with `internal DailyV1TraitDefinition(string typeToken, string definitionId, string displayName)`, and the parallel public sealed `DailyV1CapabilityAttributeDefinition` with the same internal constructor shape. Both expose immutable `DisplayName`; use exact type tokens `TraitData` and `CapabilityAttributeData`. Add private frozen `IReadOnlyDictionary<string, DailyV1TraitDefinition> traits` and `IReadOnlyDictionary<string, DailyV1CapabilityAttributeDefinition> capabilityAttributes` plus public immutable read-only accessors `Traits` / `CapabilityAttributes`, matching the six existing definition maps. Public immutable definition nodes are not owner/Store exposure; constructors stay internal and only the graph factory creates nodes. Extend the existing `CreateSelectedSchema` factory with `IEnumerable<KeyValuePair<string,string>> traitDefinitions` and `capabilityAttributeDefinitions`, where each pair is exact authored DefinitionId → effective fallback DisplayName. The Unity adapter builds these pairs directly from admitted `CaptureAssets` values after each asset's `TryValidate`; sort ordinal by the existing asset key before passing them. The factory creates exactly one canonical node per pair and `Freeze` rejects duplicate IDs. Thread those exact maps through `WithContentProjection` and the internal copying constructor so projection attachment preserves node identity. This adds no standalone map, public store, owner-local interner, or synthesized empty asset.

- `DailyV1CapabilityAttributeDefinition`: `DefinitionId`, `DisplayName` (same authored fallback: blank display name → ID), and existing non-empty-ID validation.
- `DailyV1TraitDefinition`: `DefinitionId`, `DisplayName` (blank trait name → ID), and existing non-empty-ID validation.
- Add the corresponding canonical maps to `DailyV1EffectiveDefinitions`. `CreateSelectedSchema` accepts the converted `{id, displayName}` inputs; .NET fixtures accept those same value inputs when present. Never create empty stand-in nodes for absent assets.
- Retain typed values' ID fields and order. At selected-profile admission validate/resolve `DailyV1NpcData.traits`, each `DailyV1CapabilityAttributeValue.attribute`, each `DailyV1ItemData.capabilityModifiers[].attribute`, and optional model configuration references through the same graph maps. The executable capability consumer stores the resulting canonical nodes and compares them by `ReferenceEquals`, matching ScriptableObject reference behavior; ID strings remain stable input/wire identities. P12 codecs keep ID rows and resolve IDs via those maps during detached hydration. Do not extend the selected profile or P12 owner rows.

The exact existing adapter/factory inputs are Unity `TraitData.DefinitionId` plus `.DisplayName`, and `CapabilityAttributeData.DefinitionId` plus `.DisplayName`; the adapter is their only Unity reader. Existing `DailyV1NpcData.traits`, `DailyV1CapabilityAttributeValue.attribute`, and `DailyV1CapabilityAttributeModifier.attribute` stay ID strings in the copied schema and bind only through the graph. No authored field or `GenericCapabilityModelConfiguration` asset is added to `SimulationConfigData`.

`GenericCapabilityModelConfiguration` is not a `SimulationConfigData` member. Source search found construction only in tests (`CapabilityFoundationTests`, `ConflictConsequencesTests`, `ConflictFoundationTests`) and no production composition path; do not fabricate a Daily-v1 default. Its existing optional engine-free contract is exactly physical/mental attribute IDs, `physicalWeight` (`1f` default), `mentalWeight` (`0.5f` default), and ordered `{traitId, attributeId, additiveValue}` rows. Preserve the current real consumer semantics: base values match configured attrs by reference; NPC traits match modifier trait by reference; each unique inventory item contributes its item modifiers; context modifiers and `ICapabilityConditionSource` apply in current order; breakdown source IDs/order and Unity `Mathf` behavior stay unchanged. Core resolves these refs to canonical trait/attribute nodes. Preserve validator outcomes: valid distinct physical/mental refs (including current ID-distinct check), finite nonnegative weights, valid trait/attribute refs, finite nonnegative additive values, duplicate `(traitId,attributeId)` rejection, unique valid NPC traits, and valid NPC/item capability refs. No stub/default evaluation.

`TraitData` / `CapabilityAttributeData` remain Unity authoring assets and keep exact serialized fields and `.meta` GUIDs. The adapter resolves each admitted reference via Unity fake-null (`asset == null`) before conversion, detects two distinct same-type same-ID objects with `ReferenceEquals`, interns one Core node, and rejects unbound/wrong-family IDs before any runtime allocation. The selected fixture having no such assets does not prove the optional path or the source compile dependency can be stubbed or widened.

## Assembly, serialization and compatibility

- Move semantic owners, selected consumers, P12 encoders/hydrators, `SimulationRuntime`, active-session/application and required accessors together into the one `Simulation.Core` assembly; keep semantic internals `internal`. Unity and .NET compile the same source once each; explicit SDK `Compile` items plus Unity `noEngineReferences` asmdef. Keep Unity adapters/authoring assets and their `.meta` identities in Unity. No engine stubs, copied domain rules, blanket `InternalsVisibleTo`, second runtime, public Store API or mod surface.
- Resolve the `[Serializable]`/`[SerializeField]` fields from the actual bootstrap owner: `TesteSimulacao` keeps `[SerializeField] SimulationConfigData`, but `npcRuntimeList`/`cityRuntimeList` and definition-index maps are private runtime-only fields without `[SerializeField]` (`TesteSimulacao.cs:106,113–114`). Genesis stages clear/rebuild them (`532–558`, `1921–1947`, `2121–2140`); success and restore call `ReleaseBootstrapAliases` (`688,864,1018+`) which drops those aliases. No production `JsonUtility` path serializes these owners; P12 uses explicit ID codecs. Therefore Core owner-to-definition/row references become private non-Unity-serialized fields (remove their `[SerializeField]`), are recreated from the one effective graph on genesis, and are resolved from that same graph by P12 hydration. Do not annotate graph value types with Unity serialization or retain a shadow ScriptableObject reference. Keep all authored ScriptableObject schemas and `.meta` GUIDs exactly; Unity tests cover bootstrap reconstruction and authoring asset schema. Existing JsonUtility tests concern detached continuation DTO/payload behavior, not runtime owner object persistence.
- Preserve the selected profile ID `UnityBootstrap-Daily-v1`, P12 family/section IDs, wire versions, `DefinitionId` bytes, operation order and Unity v1 descriptor semantics. The move emits new truthful Core/host assembly MVIDs; never forge old assembly identity or imply cross-build/cross-host slot compatibility. The approved v2 identity must be integrated end-to-end through continuation header/image/codec/store/atomic reread and rejected before staging on host mismatch. Unity v1 old-slot compatibility remains governed by exact approved descriptor contract and golden byte vectors, not an invented exception.
