# User authority · Authoring and intervention handoffs

## Dungeon Studio source facts and smallest proving design

Inspected local `codex/dungeon/studio` at `b3ebfaa89cb91958a3908a6bdf96509416735878` without changing that checkout. Its schema-5 Draft state and strict Validated state are real local source. The older publish branch `e360ec83da8c8ef349e2c9327490291ff457112c` and repository canonical architecture do not establish delivery of schema 5.

- `DungeonStudio/src/Dungeon.Core/AuthoringDocumentValidator.cs`: `ValidateDraftForAuthoring` accepts only schema 5 Draft and filters exact physical diagnostics such as corridor contact, room overlap, portal boundary or derived connectivity mismatch. It still validates structural references, unique IDs, version, size/bounded canonical simple rings, door identity/count/order, floors, containment and spline structure. It is not a blanket invalid-data or all-geometry waiver. `SplineRouteGeometry.TryValidateAuthoringStructure` and the editor fallback must be assessed separately from materialized valid geometry.
- `DungeonValidator.ValidateForSimulation` requires strict physical validation and `Validated`. `EditorCommandApplier.PromoteAuthoringDraft` validates Draft structure, rematerializes supported splines and validates the candidate as schema-5 Validated before committing. `EditorSession`/ViewModel wire the strict promotion and current “simulation-ready” label. That label describes the local validity boundary. It does not establish an importer or guarantee the availability of a Simulation runtime capability.
- `DungeonStudio/src/Dungeon.ProjectFiles/ProjectJsonCodec.cs`: `ReadForAuthoring` and `WriteAuthoringDocument` handle safe Drafts. `ReadAndValidate` and `WriteCanonical` are the strict path and keep their existing behavior. Source `Model.cs` has two states, Draft and Validated. Existing Draft files have no explicit acceptance.

Keep both document states and strict validators. The recommendation is a **separately versioned accepted authoring artifact**, containing or durably resolving the exact canonical schema-5 Draft bytes, document/project identity, schema/profile and digest, acceptance identity and responsible author, the exact acknowledged exception and affected element IDs, diagnostic/classifier version and a named projection contract. It can use existing editor canonicalization of Drafts. This is an explicit action on one reviewed revision, not a new document enum or reinterpretation of Validated. A durable accepted artifact retains the original exact bytes and original diagnostics or reproducible identity. Editing leaves that older artifact intact and requires explicit reacceptance before exporting the new revision. Never accept existing Drafts automatically. Legacy projects may follow the existing explicit authoring conversion when desired. Schemas 1–4, procedural generator output, generation vectors, strict v5 Validate Geometry and safe file handling retain their meanings. The new authoring acceptance must never route through a geometry repair/rematerialization command or invent data to make the strict validator green.

**First bounded proving case.** Accept exactly one intentional interior crossing between two structurally valid stored corridors with stable independent explicit connections. Prefer a fixed stored-footprint fixture with valid portals and fully connected explicit topology. Require sane rings and unchanged endpoints, physically supported portal segments away from the crossing, no unrelated contact/overlap or other strict failures except the identified pair's crossing. The precise crossing classifier and supported route representation are the scope of the Dungeon technical design. A broad Draft allowlist or generic `geometry.corridors-touch` code alone cannot establish that the diagnostic belongs to exactly the accepted pair. Unrelated contacts and structural errors reject. Keep the UI acceptance and diagnostics distinguishable from physical validation. Round trip the accepted package bytes, intent, stable IDs and retained diagnostics, verify stale or tampered input/digest rejection, legacy file/strict regressions, undo/edit separation, duplicate/dangling/reference/geometry rejection and atomic save failures. Confirm that the logical graph is identical across acceptance, with no new edge at the overlap. No runtime code or Simulation importer is required to prove this authoring slice.

## Consumers and unsupported geometry

| Consumer | May consume after its own admission | Refusal or fallback |
|---|---|---|
| Dungeon/City editor and read-only viewer | Exact structurally valid drawing or authoring document, with honest origin and validation/acceptance status. | If physical materialization is unsupported, use a supported stored footprint or factual/diagnostic panel. Never label it a physically coherent layout. |
| Future explicit topology projection | Typed places, containment and explicit connections via reviewed graph-only interchange. Preserve source/digest, projection/loss declaration, accepted exceptions, ID/owner/namespacing map, and explicit traversal semantics if the target contract supports them. | A crossing, overlap, fallback polygon or render order proves no junction, adjacency, wall passability, floor transition, path metric or accessibility. Unsupported graph/placement contracts reject before publication. |
| Geometry-derived runtime operations | Only the exact capability proved by a compatible geometry validator and target profile. | Refuse or mark unsupported for collision/navmesh, physical route tracing, geometry-derived travel duration, visibility, occupancy/classification or position sampling when unsupported. A validated logical routing operation may be available on explicit edges if its semantics require no ignored geometry and the Core contract expressly admits it. |
| Simulation state adoption | A separate authorized Core genesis or runtime transaction using actual registered P8 Location/AnchorHex and explicit site/topology owner identity. The import must validate graph shape and target relationships and install only admitted facts. | Studio acceptance records intent but does not confer Core authorization, simulate occupancy or compose a profile. Staged rejection leaves prior world unchanged. No P10 or Daily-v1 scope change. |
| Atlas / LAB-OBS-A | A documented preview or approved facts at a coherent cut, with document digest/binding and provenance only where supported. | Preserve authored-vs-runtime label and missing capabilities. No fabricated positions, causal events or Atlas write path. |

P8 canonical `470667d37863384edadb3d93ef64d8004aff46a3`, `SpatialAuthority.cs`, indexes axial coordinates and exact Location anchors. P10 canonical `e53252de5277fd5af46bbacb8eda5ee6e74aff08`, `RuinLocalTopologyGeneration.cs`, `P10BGeneratedRuinGenesis.cs` and `LocalTopologyFoundation.cs`, supplies the existing bounded semantic graph and private composition. It does not derive polygons or paths from a Studio overlap. Keep P10-B seeds, IDs, generation versions and existing excluded Daily profiles. A compatible consumer must declare an explicit mapping to P8/P10 owners or fail. No automatic use of a Draft or accepted artifact as a P12 representation.

**Future City Studio** can reuse document/acceptance/projection distinctions and visual conventions. A road drawn over a building or buildings with overlapping footprints may be explicit in a valid authored representation. Those shapes establish neither road connectivity, traversable building entrances, ownership, residence nor actual occupancy. City topology, permissions, possession, occupancy and physical authority get separately owned contracts when a consumer is chosen. City Studio stays deferred.
