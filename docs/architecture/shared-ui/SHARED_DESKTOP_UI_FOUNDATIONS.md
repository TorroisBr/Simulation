### Architecture comparison and reuse decisions

Paths in the table are relative to `WorldAtlas/` and `DungeonStudio/`, respectively. The two desktop projects target `net10.0`. Atlas UX pins Avalonia 12.2.0. Dungeon Studio pins 12.1.6 and keeps `Dungeon.Core` and `Dungeon.ProjectFiles` at `netstandard2.1`.

## Boundaries and project layout

Application composition roots opt in. Dungeon Studio owns authoring, coordinates in document units, geometry validation and document/command lifecycles. Atlas owns immutable factual presentation, coverage/provenance and supported observation routing. City Studio will own city authoring. Shared presentation never establishes City placement, world connectivity, authored document validity, simulation state or command authorization.

```text
SharedDesktopUi/
  src/Simulation.Ui.Viewport/              net10.0, framework types only
  tests/Simulation.Ui.Viewport.Tests/      net10.0, pure .NET tests

  Future, after compatible second-consumer evidence
  src/Simulation.Ui.Avalonia/              opt-in resources and small layout primitives
  tests/Simulation.Ui.Avalonia.Tests/      Avalonia headless + consumer-native checks
```

First dependency direction: `WorldAtlas.Observations → Simulation.Ui.Viewport ← Dungeon.Studio`. World Atlas Desktop continues to depend on its Observations project. The portable observation assembly can call the pure helper without importing Avalonia. Dungeon Studio's existing dependencies on Dungeon.Core and ProjectFiles remain. The shared projects must have no dependency on either app, Unity, Simulation Core, Lab, World Exchange, P12, or any document/observation model. Future City Studio can choose a compatible shared release. There is no shared app host, view-model base, DI container, navigation service, selection store, event bus or global settings store.

Start with exact source `ProjectReference` inside each repository checkout. Keep the shared source in one dedicated implementation commit and apply that unchanged source to each compatible consumer base. Record the shared commit/tree and consumer base in each review. Each app still builds, tests and publishes from one checkout and owns its target framework, SDK lock, central package pins and app version. CI verifies the project is reachable with a clean checkout, no sibling worktree or local feed. Keep the API additive across early consumers or update each opt-in explicitly. Independent release cadence may later justify SemVer packages on an approved feed with exact consumer pins, committed restore locks, source mapping where used and published source provenance. This review adds no feed. A future Avalonia-dependent package requires version-matrix validation and an explicit supported range. There is no shared Avalonia upgrade in the viewport slice.

## UI scale and visual conventions

- Treat OS/per-monitor DPI, app UI preference and camera zoom as independent. Window layout, padding, hit targets and pointer positions use local DIPs. Native rendering applies platform pixel scaling once. Apply app preference to the base typographic sizes, action minima, spacing and chosen map label resources. It must never rescale document coordinates or observation geometry. Preserve the pointer-to-map transform across DPI transitions, using current Avalonia DIP coordinates rather than device pixels. Round presentation values only where the app already has a reviewed rule.
- Use semantic roles for surface, raised surface, border, primary and secondary text, accent, selection, focus, error and warning. Standardize body, small, section and title typography roles and hierarchy. Atlas keeps its dark palette and Dungeon its light palette. Preserve domain encodings and accessible state distinctions within each palette. Put any future shared resource dictionary under a namespaced opt-in include controlled by each app. No global Fluent replacement or shared preference file. Retain OS/system font fallback. App copy, fonts and colors stay under consumer acceptance.
- Define readable panels with a stable header, scrollable body and a visible action/footer when applicable. Let app constraints adapt to the owner monitor work area, available DIPs, larger type, long content and localization. Keep hover/focus/pressed styles from changing measured size. Preserve title, modality, Escape/cancel/default policy, return focus and keyboard order as owned by the app. The fixed Atlas About dimensions are evidence for that accepted case. Smaller displays and larger type require separate fit validation before reusing its shell.
- Provide a visible focus indicator, reachable named controls, a keyboard path for inspection and actionable information without requiring pointer hover, and status conveyed in text as well as color. Ensure shortcuts respect a focused text input and dragging or modal interaction. Use appropriate native controls before adding a custom shared control.

## Checkpoints and order

1. **Shared viewport math.** Pure library, tests and two bounded consumer adapters. See the [technical handoff](SHARED_DESKTOP_UI_HANDOFF.md). Shared library work can be prepared in isolation when separately mandated. Atlas integration waits for ATLAS-A canonical promotion and verification of the actual accepted UX base. Dungeon integration waits for a stable selected spline/MapCanvas baseline and agreement on exclusive ownership of that source hotspot. Each consumer may validate and integrate independently. Close the slice after both are accepted on the exact shared source.
2. **Opt-in visual resources and Inspector layout.** Deferred until the two app owners agree on a small common token set and confirm named live consumers and supported Avalonia versions. If justified, start with the token dictionary and one existing read-only/presentation section per app before considering a control. App acceptance of contrasts, focus and scale precedes adoption.
3. **Dialog or numeric-edit primitives.** Future independent designs after their respective two-consumer evidence. A bounded dialog body can be evaluated independently of a numeric edit control. Neither depends on City Studio. Gesture or input extraction remains out of scope until specific shared behavior is stable.

The pattern guidance is available now. CORE-F closure, ATLAS-A acceptance and promotion, Dungeon spline development, and LAB-OBS-A dependencies do not acquire a shared-UI dependency. LAB-OBS-A and ATLAS-B keep their existing producer/consumer gates. City Studio remains deferred.
