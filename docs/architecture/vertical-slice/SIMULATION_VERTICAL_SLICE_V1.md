# Simulation Vertical Slice v1 · Reviewed roadmap candidate

This is the integration scope and handoff for the first functional ecosystem. It does not itself authorize code, change a numbered Phase contract, promote a candidate or select a new P12 profile. Architecture base `cb71a70fc503e926c3b3f39415b86f2fab896ba8`. The [local live-session contract](VERTICAL_SLICE_V1_LIVE_SESSION.md) and [City foundation scope](VERTICAL_SLICE_V1_CITY_FOUNDATION.md) specialize this roadmap.

## Product boundary and acceptance

One controlled local offline Windows x64 Atlas test bundle launches one fresh Core-owned selected Daily-v1 world and displays completed cuts. It starts paused after the first successful day. Select authoritative Hex, Location and City facts, step one day, then resume at Slow, Normal and Fast speeds, pause at a completed boundary and inspect actual stock. Atlas is the first interactive frontend. Core and Lab remain independently usable.

Generate, edit, save and reopen one supported native Dungeon in Dungeon Studio. Open the same unchanged validated file in Atlas-C and return to the selected world view. Generate, save and reopen one small City in an independent City Studio and open the unchanged validated file in the bounded City Viewer. Both document views declare their document origin, IDs and local coordinates. The integrated demonstration uses real P8 Hex → Location identity and the actual City roster, including unbound Cities. Standalone documents have no WorldId, CityId, site or Location association. A cross-link to generated geometry is deliberately out of v1 because no admitted selected profile can currently prove the required mapping. Advanced generation, City editing, dynamic geometry, shared persistent worlds, saves in Atlas, historic reconstruction, causal event streams and interventions are outside the first acceptance.

## Meaning and authority of generated places

A Studio document is a reproducible, validated authoring artifact, identified by document ID, immutable canonical bytes/digest, schema and generation provenance. The exact document may be opened offline in any compatible viewer. A Core Location or site has its own authority and lifecycle. A file, filename, overlapping coordinates, label or user selection alone establishes no association.

A future bounded attachment should first prove one existing admitted Core world/site or City and a real P8 Location, plus one exact document of a matching capability and schema. The responsible Core operation validates and persists the explicit binding, qualified ID mapping and provenance, with coherent read coverage. The current selected Daily-v1 City definitions have no material-flow LocationId. No P10-B topology or new binding owner is admitted implicitly. That future work requires its own profile, persistence and reconstruction decision.

For evolving worlds, keep imported immutable base bytes separate from runtime-owned typed facts such as a blocked passage, building condition or a replacement geometry revision. A block is not a geometric rewrite. A coherent reader may later project a supported fact keyed to the explicitly mapped element and boundary. When physical geometry really changes, the owning runtime operation must validate the new state and preserve recoverable inputs, identity/provenance and exact boundary semantics. It may publish a new matching geometry artifact or overlay under a reviewed capability. Frontends display the current compatible cut while the base document remains available. Studio processes are never runtime dependencies. No generalized revision graph or live authoring bridge is needed now.

Future Atlas interventions follow the [approved Core authority contract](../USER_AUTHORITY_WORLD_RULES.md), with supported typed requests/declarations, admission, structural integrity, provenance and durable input handling. They remain distinguishable from autonomous events. No intervention implementation is part of v1.

## Runtime support and distribution

The current net8.0 host is a known Core compatibility target for the controlled local proof. Microsoft ended .NET 8 support on 2026-11-10. Before distributing a supported live bundle, separately qualify a supported SDK and runtime, preferably .NET 10 LTS with the same fresh genesis-only application semantics. The current v2 compatibility descriptor/admission is hard-bound to net8.0. Do not alter its persistence contract just to host live controls. This qualification can be designed in parallel and is a distribution dependency, not a prerequisite for approved Core/Lab evidence work or the local slice. [Microsoft .NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

## End-to-end scenario and exit criteria

1. Launch the supported offline Atlas bundle. Start one selected real world. Display the successful Day 1 cut in paused mode, with WorldId, geography and owner revisions. Select Hex and actual Location through the registered anchor. Select Campo Verde via the roster and inspect TRIGO 450 with City location unavailable. Confirm Serra de Ferro also has no P8 binding.
2. Step once. Verify same WorldId, exact Day 2 and sequence +1, stock 480, and observed difference +30. Complete several further true days at all three paces. Pause with a deterministic completion acknowledgement, ensure no further advance is admitted, resume and verify unchanged per-day outcomes against an ordinary host control with equivalent inputs. A change in cadence must not change boundaries or facts.
3. Run Lab's separate offline two-day producer and open both accepted native artifacts in Atlas. Verify same-run audit and comparable stock/coverage within that run. Independent runs allocate distinct WorldIds. Check canonical byte/provenance tests, unbound City behavior and real-reader convergence for live/file inputs.
4. Generate an admitted Dungeon, make one valid edit, save and reopen with Dungeon Studio. Open in ATLAS-C with exact display digest and select a real room/passage. Generate a City via City Studio, save and reopen, and open the exact displayed graph/lot/building values in Atlas. Observe standalone provenance. Return to the existing world view and verify navigation/focus, world identity and the last displayed boundary.
5. Exercise malformed files, refusal of unsupported association, wrong/completed/faulted advance, one in-flight step on close and abnormal child exit. Verify no accepted cut from failures, no silent restart, no orphan process and no claim about unseen post-fault changes. Validate locked builds, complete safe evidence, native paths, independent source review and run limitations.

No new product choice is needed to continue this design path. A decision to make a bound generated place, save/resume across launches or a different starting profile mandatory would change the slice and needs a separately scoped approval. Current real blockers are the promoted facade and producer, Atlas real reader, completion of the Viewer, City technical design and subsequent implementation. Crypt native acceptance remains with the user for that separate checkpoint.
