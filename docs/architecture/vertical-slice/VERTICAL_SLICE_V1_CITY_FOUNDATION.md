# Vertical Slice v1 · City Studio foundation

**Readiness** · Entry scope for bounded technical design. The wire schema, precise limits, generator version and source pins require review before implementation. This scope covers one independent City Studio and one later read-only Atlas view. It grants no authority to create a Simulation City or place one on a Hex.

## Smallest useful proof

Generate a compact orthogonal neighborhood on one plane from a bounded seed, one fixed versioned rule set and simple rectangular bounds. Create a connected street graph with a primary street and a few intersecting cross streets, then derive rectangular blocks, split each block into street-fronting lots and place a bounded setback building footprint per occupied lot. Expose Generate, seed, map fit/pan/zoom, document facts, Save and Open. Demonstrate visibly different accepted seeds in the same generator version. Preserve seed, effective ruleset and result digests. No terrain input, multi-floor, lot markets, arbitrary polygons, editor tools, occupation or growth.

Separate the City-owned typed document, deterministic generator, strict validation and portable codec from the Avalonia host. Choose a small pure City geometry/document assembly and file codec, built and tested without Unity. Use the existing Shared Viewport for presentation. Follow proven Studio practices for staged open, canonical bytes, atomic save and artifact provenance. Reuse a domain-neutral primitive only after its actual contracts match. Do not reference Dungeon.Core, import Dungeon validators, manufacture a Dungeon-style Room/Passage graph or extract a shared Studio framework. City Studio remains runnable and distributable separately.

Current `DailyV1CityDefinition` and `DailyV1CityRuntimeOwners` own simulated City facts and material flow. Their authored entries and runtime IDs do not identify a street, lot or building footprint. `LocationRecord` gives coarse geography and `RuntimeStructureTruth` supplies a separate inert construction record. All IDs in this City document are local to it. Neither P15 Structures, households, occupancy, ownership, traversability in Core nor City-to-P8 placement can be inferred from this layout.

## Research and choice

| Alternative considered | Applicability |
| --- | --- |
| Adapt proven staged urban generation | Parish and Müller use road generation followed by allotment and building geometry. Adopt the stage order and bounded constraints, using simple straight orthogonal streets rather than a general L-system. The paper is an algorithm reference. No commercial CityEngine code or assets are used. [Procedural Modeling of Cities](https://people.eecs.berkeley.edu/~sequin/CS285/PAPERS/Parish_Muller01.pdf) |
| Adapt parcel subdivision | Vanegas et al. demonstrate subdivision inside blocks and evaluate parcel properties. Use straightforward integer frontage subdivision for rectangles. Its fixed geometry is enough for the slice. Oriented boxes, straight skeletons and parcel remapping become relevant only with irregular blocks or editing. [Procedural Generation of Parcels in Urban Modeling](https://cs.purdue.edu/cgvlab/www/publications/vanegas2012procedural/) |
| Reuse NetTopologySuite | Its JTS-derived predicates and operations would merit evaluation for arbitrary polygon overlays and subdivision. Rectangular axis-aligned inputs need only bounded integer intersection/containment checks. Adding a general geometry library here would introduce precision policy, determinism, dependency and validation costs. The repository has published license and attribution terms to verify at a specific release if reconsidered. [NetTopologySuite](https://github.com/NetTopologySuite/NetTopologySuite) · [License](https://github.com/NetTopologySuite/NetTopologySuite/blob/main/License.md) |
| Extend Dungeon | Reuse the architecture and tested operational patterns. Dungeon's spatial rules, traversable portal semantics, schema and geometry types would bind City semantics to a different domain. Use an independent City document and the shared presentation-only transform. |
| Custom general generator or constraint framework | Defer. A constrained combination of grid roads, rectangular subdivision and setbacks meets this first target. WFC, grammar-driven expansion, irregular road graph and urban growth need separate proving requirements. |

This is an adaptation of established methods with original application integration. No additional geometry or generation dependency is adopted in this scope. Future adoption evaluates actual license, supported platforms, offline use, exact numerical behavior, maintenance and replacement cost.

## Invariants for technical design

- Freeze a generator ID/version, RNG/seed derivation, exact effective rules/units, canonical ordering, codec version, bounded sizes and deterministic IDs. Reference graph nodes/segments, blocks, lots and footprints explicitly. Define ID scopes and uniqueness. Same compatible inputs produce the same normalized City and golden bytes. A document revision/digest is distinct from generator identity and from any future Core identity. A different ruleset or algorithm affecting golden output requires explicit versioning.
- Use signed bounded integer local coordinates and exact edge rules. Reject zero-length segments, duplicates, dangling endpoints and accidental unnoded crossings. Validate connectivity, positive bounds and frontage, nonoverlap of lot interiors, footprint containment and separation from street rights-of-way. Presentation cannot fill missing records. Use one strict validator for generator output and loaded files.
- The codec design must specify strict format and supported profiles, size/depth limits, canonical serialization, stable reference order, explicit validators and failure-atomic open/save. Stage the whole document before publishing UI state, retain previous view on failure, and reopen exact bytes without re-generating. No hidden migration or automatic file overwrite. Exact schema, street right-of-way representation and numerical limits belong in the next technical design, not worker invention.
- Require clean locked build and offline Windows x64 Studio, pure .NET generator and validator tests, cross-process round-trip equality, seed variation, checked numeric limits, malformed/oversized/unknown version and invalid geometry negatives, stable picking and viewport-fit tests, and native Generate → Save → Open → Inspect. Test with no Atlas, Core or Dungeon process/pack present.

## Minimum City Viewer

After the City library and one fixture profile are reviewed, Atlas Desktop consumes the pinned City codec and scene semantics through a narrow read-only pane, with City-local coordinates and typed street/lot/building IDs. Open one explicit local validated artifact and show document origin and selected element facts. Preserve world camera, selection and focus when returning. Reuse the successful ATLAS-C host behavior and Shared Viewport with separate City validation/domain. Core, City Studio and the generator do not run in the viewer. Malformed, unsupported and unvalidated inputs fail closed. Use exact file and displayed digest identity, no persistence side effects and native offline acceptance. A document with a future authoritative association or runtime overlay requires the separate binding and factual projection described in the [roadmap](SIMULATION_VERTICAL_SLICE_V1.md).

General Architecture owns the seams. Dungeon Studio Arquiteto contributes City design and experience without becoming a Dungeon dependency. Assign a City implementation owner after a reviewed technical design and dedicated mandate. Atlas Orchestrator owns the later viewer. Simulation UI Orchestrator retains the pure viewport mandate. No additional shared UI work is a City entry gate.
