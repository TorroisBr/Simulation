# Vertical Slice v1 · Local interactive Daily-v1 session

## Reuse and first host

For controlled local testing, use the official net8.0 `Simulation.Lab` executable, with one separate local interactive mode beside the existing finite-source and approved file-producing modes. Atlas net10.0 launches the pinned, packaged Lab executable directly over redirected private standard input/output. Lab is also runnable without Atlas. Core has no Atlas, Avalonia or protocol dependency. The existing identity adapter enforces .NETCoreApp v8.0 for the entry assembly and captures actual runtime, entry and anchored identities. Qualify the deployed .NET 8 runtime and entrypoint through the real factory. Do not simulate host identity, roll into .NET 10 by assumption or ship the test verification host. Use OS child-process primitives and explicit direct launch. Microsoft documents asynchronous stream drainage to avoid redirected-pipe deadlocks. [Process redirection guidance](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.redirectstandardoutput)

Future native C# adapters can reuse the same narrow commands on a qualified host. A local multi-client need may justify OS pipes or a local service, with single ownership and explicit access rules. A remotely hosted Lab application could later expose HTTP request/response commands and WebSocket delivery of detached observations behind an authenticated, reviewed server adapter, with ordered single-writer admission. A browser can consume these application protocols while Core stays on the server. None of these transports changes domain time or grants an extra advance owner. [Microsoft local IPC guidance](https://learn.microsoft.com/en-us/aspnet/core/grpc/interprocess?view=aspnetcore-10.0)

Microsoft lists .NET 8 as out of support since 2026-11-10. Keep the accepted net8 runtime path for the existing verification, offline work and isolated local proof. A supported distributable live host needs a separate qualification. Prefer a bounded .NET 10 SDK-only entry that reuses the existing no-save Core genesis preparation, graph binding, publication and advance/capture contracts. Qualify the actual runtime, build identity, selected scope, parity and failure behavior. The identity constructor/factory and P12 v2 admission currently require net8.0. Do not treat changing an SDK target or rolling forward automatically as qualification, and do not widen save/restore or claim cross-host P12 compatibility. [Microsoft .NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

## Application operations and ownership

- **Start and first cut.** Explicit Start creates a private empty no-save root and calls the promoted equivalent of `DailyV1LabObservationRun.TryStart` with real Lab entry identity. No caller configuration, seed, restore path or scenario selector. One fresh WorldId per run, plus distinct producer runId. The Start contract visibly includes one genuine `AdvanceAndObserve` for the first captured completed day. Publish Day 1 and start Paused. A failed start/first capture yields no live view and no automatic retry.
- **Advance one day.** Validate transport correlation and expected active run/exact last boundary before admission. Execute the same Core-owned `AdvanceAndObserve` exactly once per admitted demand, with its current reservation, exact-session completed token, sealed census and owner-thread read. Return detached geography, City, Market and provenance for that cut. Day, sequence, scope and WorldId must be correct. Atlas entity selection and queries work from the detached current view. No arbitrary store query, save/load slot, intervention or intraday port is exposed.
- **Close.** Stop further admission and let any single in-flight operation settle. Dispose the run on the exact creating owner thread after the operation exits. Return orderly stop, close pipes and reap the child. Missing replies/EOF, timeout or crash fault the local run and freeze the last proven view. A bounded shutdown waits for the child to exit normally first, then may terminate only the owned stuck child. Do not retry/reattach, launch duplicate children or report rollback. Clean only the run-owned scratch root after process exit. Application create, calls and dispose all happen on one fixed thread. Any async transport IO marshals messages to that thread. Thread-pool continuations and UI/render callbacks never enter the Core facade.

The narrow process contract has Start, AdvanceOneDay and Stop requests, a mutually validated version, monotonic request identifiers independent of WorldId/runId/observation index, and exactly one bounded reply per accepted frame. Use one connection to the child through redirected stdin/stdout, with no user-supplied endpoint, startup command or arbitrary path. Frame lengths are checked before allocation. Body is exact observation bytes capped at the existing 4 MiB plus a small separately bounded control header. Keep diagnostics on stderr and drain it independently with bounded retention. Reject invalid/version-mismatched, duplicate or stale requests before another advance. An invalid or ambiguous reply never grants a replay. Pin actual framing and error codes in the technical handoff and test EOF, malformed lengths, bounded drains, timeout and process lifecycle. No pooled multi-client dispatcher or general transport library.

## Playback and factual presentation

The Atlas controller schedules the next ordinary one-day demand at Slow, Normal or Fast intervals using monotonic wall time measured after completion/validation. Start Paused, advance one day while paused, and choose a documented fixed ordered interval for each preset. At most one request is in flight. There is no time debt, timer queue or catch-up burst. Changing speed never adds a simulated input or changes any deterministic rule. A Pause issued during a day displays Pausing, drains that day, and acknowledges Paused when no further step can be sent. Resume submits new steps at the selected pace. Session close stops scheduling immediately and handles the same in-flight boundary. Opening a Studio document while live requires the run to settle Paused first. The child stays alive and the last world selection remains available on return. Repeated clicks, stale results and application close cannot double-advance.

An accepted result is the existing detached LAB-OBS-A cut serialized with the promoted [v1 contract](../world-atlas/LAB_OBS_A_OBSERVATION_V1.md) by the same producer implementation. Reuse the exact selected capabilities, canonical token and build/input provenance. Lab's offline command still publishes exactly its two files after atomic rename. Live mode serializes the same wire profile across consecutive successful cuts with its own runId, index and predecessor linkage, starting at zero. Keep exact payload bytes including LF for digest matching. Preserve sequence continuity and compare only adjacent and compatible cuts. If transmission or validation fails after advance, the prior view is stale and the run stops, even if the current day completed in Core. A disconnected run cannot infer stock or world facts. Live/file source labels, status and scope remain visible.

The offline writer, local live encoding, ATLAS-B real byte reader and native UI are separate responsibilities. Use one Core projection and one approved producer encoding seam before both producer modes. Reuse `WorldAtlas.Observations` byte parsing and comparison for live and file data. ATLAS-A's Demo-only checker is the existing seam, with no second live parser or duplicate facts model. The Lab live host design can proceed while the Atlas team closes ATLAS-B. Live acceptance depends on the reviewed real reader and encoding, plus its own host/native checks. The full offline UI need not be on the live critical path.

Larger elapsed simulation uses successive supported days first. A future batch may reuse Core's already admitted multi-day entry after a separate read/partial-failure/interruptibility design. Finer steps require a supported temporal profile, approved chronological boundaries, owner/admission and coherent reader. Speed choices do not establish that capability.

## Validation to carry into implementation design

Prove foreground responsiveness, pinned runtime/executable, locked publish, same Core run and whole observation digest under file/live conformance, correct +1 boundaries, immutable cuts and classified failure. With real input and ordinary advance control, check Day 1/2 450/480, successive days beyond the baseline, equivalent outcomes at different scheduling speeds and fresh WorldId semantics. Test pause while waiting and in flight, no extra tick or double click, wrong thread and wrong session, disconnect/timeout/child crash after possible commit, close with one active advance, pipe backpressure/malformed frame, clean shutdown, no inputs or custody outside the private root. Use the normal Core/Atlas/SDK validation and evidence ownership. Do not infer implementation readiness from this architecture alone.
