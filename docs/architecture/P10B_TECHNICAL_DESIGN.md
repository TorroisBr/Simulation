# P10-B — Deterministic Local Topology Generation v1

**Checkpoint:** P10-B, bounded technical design only
**Classification:** `READY_FOR_TECHNICAL_DESIGN`; this document is not implementation authorization or a promoted capability.
**Design baseline:** `f6924e63d8e5731da1d33021d0361e7defe6dad7` (promoted architecture/planning baseline; branch `codex/architecture/p10b-technical-design`).
**Scope:** one generated Ruin site at the selected P9-B canonical Location in a pre-start genesis profile. The new explicit profile contract identity is `unity-authored-bootstrap/ruin-topology-v1`; its P10 stage ID is `p10b.genesis.ruin-topology/v1`. It requires P9-B authored geography and retains the P10-A profile separately.
**Review:** independent technical review is required; author does not self-approve.

## 1. Decision and intended proof

P10-B adds one site-scoped, deterministic generator that builds a small finite graph of semantic LocalPlaces, explicit connections, containment where useful, and entry point(s). The generator selects structural features by the exact keyed graph-growth algorithm in §6, not by selecting a complete graph from a fixed catalog of whole-layout templates. A fixed published seed/key matrix must demonstrate at least two valid graphs; no pairwise uniqueness guarantee is imposed.

The generated result is part of initial World Truth and is committed through the existing LocalTopology authority before the first simulated boundary. A run with identical compatible world/genesis inputs, stable site-instance identity, effective generator rules/revision and seed context produces the same semantic topology and IDs. P10-A's fixed authored profile remains supported as a compatibility path; its `DefinitionId`-keyed single site and `Entrance → Courtyard → Inner Chamber` graph are not reinterpreted as P10-B output.

## 2. Evidence and assumptions

- `docs/SIMULATION_ARCHITECTURE.md` §69 establishes `Location → LocalTopology/SubLocation`, the distinction between anchor and domain instance, Ruin archetype versus site instance, reproducibility, structural rules rather than whole-layout selection, and separation from content. §92A requires reconstruction-ready identity/state and fail-closed P12 profile admission for new authoritative state.
- `docs/architecture/P10_P14_P20_NEXT_SCOPE_DECISIONS.md` (promoted 2026-10-03 direction), `docs/phases/PHASE10_BRIEF.md`, and `docs/ROADMAP.md` identify P10-B as design-ready, not implementation-ready; P9 ordered genesis, P8 Location/site anchor, and P10-A topology ownership are dependencies. The selected proof needs no second Location.
- `ExplorableSiteRuntime` already carries `RuntimeId`, `DefinitionId` and `Location` separately. `LocalTopologyOwnerReference.ForExplorableSite` uses site RuntimeId plus Location RuntimeId. `LocalTopologyStore` validates the owner and publishes one topology per owner; the P10-A semantic owner/index currently keys its Ruin topology by `DefinitionId` (with runtime owner identity also indexed), which must migrate to `SiteInstanceId`. `LocalTopologyBlueprint` is a mutable draft model, but `LocalTopologyBuilder.TryBuild` immediately publishes through `LocalTopologyStore.TryAddTopology`; `LocalTopologyPublicationAtomicityTests` cover all-or-none member registration within the topology store, not a transaction across site, topology and identity stores.
- P9 genesis composition exposes the canonical spatial authority and profile manifest. The generator must consume the selected profile's actual Location/anchor and must not synthesize or substitute geography.
- No `docs/PHASE10_STATE.md` exists in the baseline checkout. P10-A promotion and exact capability facts are therefore taken from the promoted direction/Brief and current code/tests; this design does not claim additional P10-A delivery.

## 3. Ownership and implementation boundary

Keep the generator pure until publication:

1. **Genesis composition owner** (the existing P10 profile composer, after P9 spatial composition) resolves the selected canonical Location and site definition, creates a stable site-instance identity, builds an immutable generation request, and stages the resulting site and topology in the private genesis draft.
2. **P10-B generator** (new small domain service, e.g. `RuinLocalTopologyGenerator`) accepts a validated request and returns an immutable `LocalTopologyBlueprint` or equivalent generated draft. It has no RuntimeIdentityRegistry/store access and cannot mutate the world, consume shared RNG, allocate sequence IDs, or read Unity objects.
3. **Existing `LocalTopologyStore`** remains the runtime authority after publication, but its current blueprint builder is not a staging transaction: `LocalTopologyBuilder.TryBuild` allocates sequential IDs and calls `TryAddTopology`, which mutates member identity registration and the topology index immediately. The current genesis pipeline also builds owners into candidate stores in stages; `publishedComposition` is exposed only at the final publish stage, but there is no P10 cross-store prepare/commit API. P10-B must therefore add an explicit P10 genesis transaction rather than claim existing atomicity. A private `PreparedRuinGenesis` holds the site instance, canonical Location binding, complete topology graph, IDs, and provenance without touching the published identity/site/topology stores. At final genesis validation, preflight all IDs, owner/anchor relationships, duplicate site-instance keys and topology rules against target stores. At `p9.genesis.publish/v1`, one synchronous `TryCommitPreparedRuin` batch operation registers the site and topology members and inserts the SiteInstanceId and LocalTopology indexes as one unit. Implement it as a bounded transaction over these stores: validate the complete write set first, apply through internal no-fail add primitives, and retain an undo journal that restores all touched dictionaries/lists/revisions if an unexpected apply failure occurs. Do not call the sequential-ID `LocalTopologyBuilder.TryBuild` for this path; add a prepare/commit overload that accepts the already-derived stable IDs. The public `SimulationBootstrapComposition` is still assigned only after the batch commits. Any failed preflight/commit leaves no P10 site, topology, place or connection published.
4. **Genesis profile admission/reconstruction owners** record the exact effective generation inputs and initial generated state under the P12 §92A contract. This is an integration requirement, not a request to add P12 persistence support in P10-B.

Do not expand LocalTopology into a dungeon framework. Keep City topology behavior and P10-A profile behavior unchanged. Do not introduce a new universal spatial/domain owner.

## 4. Identity migration and stable IDs

### 4.1 Site identity and owner-index migration

The Ruin `ExplorableSiteData.DefinitionId` remains immutable archetype/content identity. `SpatialLocationRuntime.RuntimeId`/canonical `LocationId` remains anchor identity. Neither is the site instance key. P10-B introduces a persisted semantic `SiteInstanceId`, distinct from both, and uses it as the primary key for the site instance and the LocalTopology semantic owner/index. For P10-B genesis, set `ExplorableSiteRuntime.SiteInstanceId` to this value and set its current registry `RuntimeId` to the same value, after validating global runtime-ID availability. This avoids an extra unstable alias while preserving existing registry lookups. P10-A keeps its historical runtime ID and receives the explicit legacy semantic SiteInstanceId adapter. Never rely on sequential `RuntimeIdAllocator` output as P10-B semantic identity.

Use required, explicit `StableSiteKey` in the effective genesis input. For P10-B v1 derive `SiteInstanceId = "site-p10b-v1-" + lowercase-hex(SHA-256(Frame("p10b.site-id/v1", StableSiteKey, Ruin DefinitionId, canonical LocationId)))`. The key itself is stable, nonempty and unique within the world; the DefinitionId and LocationId are bound into the derivation to reject accidentally reusing a key for a different archetype/anchor. This creates an instance identity distinct from both inputs without making either input the identity. Future instances of one archetype use distinct StableSiteKeys and canonical Locations. The bounded P10-B profile still creates one instance.

Migrate `LocalTopologyStore`'s primary semantic index/duplicate check from P10-A's `DefinitionId` key to `SiteInstanceId`. `LocalTopologySemanticOwnerReference` carries SiteInstanceId plus the anchor LocationId. `P10RuinLocalTopologyGenesis` must accept/produce that identity explicitly; it must no longer infer the site key from DefinitionId. Keep a P10-A compatibility adapter that maps its one Ruin's legacy DefinitionId to `SiteInstanceId = "site-p10a-legacy-" + DefinitionId` and preserves its existing lookup behavior for callers during migration. The adapter applies only to that historical one-instance profile; a second instance cannot use the legacy mapping. Validate that the derived ID is registered once, is not equal to the Ruin DefinitionId or canonical LocationId/adapter ID, and is available in the global RuntimeIdentityRegistry. Do not key semantic topology lookup by archetype or Location after migration.

### 4.2 Generated member IDs

Topology member identity uses stable generator keys and the exact digest scheme in §5. No generated ID uses mutable allocator sequence, draw position, object identity or display text. Existing LocalTopology semantic lookup and duplicate rejection must be changed to SiteInstanceId in the same migration as `LocalTopologySemanticOwnerReference`; retaining DefinitionId as the primary semantic index would make the new identity seam cosmetic. During compatibility, the P10-A adapter resolves a legacy DefinitionId lookup only through the one-instance P10-A profile and returns its mapped SiteInstanceId. Generated P10-B lookups require SiteInstanceId.

## 5. Deterministic generation context — exact v1 contract

The immutable effective request includes the selected P9 genesis profile fingerprint, fixed effective genesis seed (signed 64-bit value; if the existing profile selects its documented default seed, use zero), `StableSiteKey`, derived `SiteInstanceId`, Ruin DefinitionId, canonical LocationId, generator ID/version, topology-rules revision, and the v1 bounds below. Compute `RequestFingerprint = lowercase-hex(SHA-256(Frame("p10b-request/v1", P9 profile fingerprint, seedBytes, StableSiteKey, SiteInstanceId, DefinitionId, LocationId, generator ID, generator version, rules revision, "minPlaces=6", "maxPlaces=10", "maxConnections=19", "maxContainmentDepth=4")))`. Record that fingerprint and every effective field as provenance. The draw root uses the existing selected P9 profile fingerprint as an input; it does not use the request or output fingerprint, avoiding circularity. No ambient `System.Random`, Unity RNG, shared simulation RNG, process state, local time, or collection order is an input.

**Version constants:** generator ID `p10b.ruin-local-topology`; generator version `1`; rules revision `p10b.ruin-structure/v1`; identity encoding `p10b-id/v1`; draw encoding `p10b-draw/v1`. Only these exact versions are supported by this design. Unknown versions fail closed. A change to any rule, range, ordering, type, cost, byte encoding, hash, draw-key spelling or mapping changes output and must add a new rules revision (and generator version if generator semantics change); never silently change v1 behavior. Preserve old implementations to reconstruct previously generated initial worlds.

**Canonical byte encoding:** all text is strict UTF-8 without BOM (invalid Unicode scalar sequences reject). Define `Frame(f1..fn)` as concatenation of each field's `uint32` byte length in big-endian order and its exact bytes. Text fields are UTF-8 bytes; the seed is one raw eight-byte field containing its two's-complement 64-bit representation in big-endian order. The root bytes are `SHA-256(Frame("p10b-draw/v1", P9 profile fingerprint, seedBytes, SiteInstanceId, generator ID, generator version, rules revision))`. For a draw key K and retry counter C (uint32 big-endian, starting at zero), compute `D = SHA-256(root || Frame("draw", K) || UInt32BE(C))`, read the first eight digest bytes as an unsigned big-endian `uint64` X. Hashing uses SHA-256 as standardized; implement with a byte-array API supported by the Unity target (for example `SHA256.Create().ComputeHash`), never a platform random provider.

For `NextBelow(K, n)`, require `1 <= n <= 2^32`. Let `threshold = unchecked(0UL - (ulong)n) % (ulong)n` with unsigned wraparound. Recompute X with incremented C while `X < threshold`; return `X % n`. This rejection mapping is unbiased and exact on supported hosts. Each semantic choice uses a unique stable K, so unrelated draws cannot perturb it. Exhausted `uint32` retry counter is a hard generation failure.

**Stable topology member keys and IDs:** nodes have keys `place/000000` for entry and `place/000001`… in generation order; edges have `edge/<origin-node-index>/<destination-node-index>` in numeric order. These keys are semantic positions in this generator's algorithm, not display labels. Derive each LocalPlace ID as `"place-p10b-v1-" + lowercase-hex(SHA-256(Frame("p10b-id/v1", SiteInstanceId, rules revision, "place", local key)))`; connections analogously use prefix `connection-p10b-v1-`, kind `connection`, and canonical directed edge key. The SiteInstanceId derivation is in §4.1. All ID tuple elements are strict UTF-8 text fields under the `Frame` function. Topology has no standalone persisted ID in the current owner contract; do not invent one. Detect duplicate generated IDs and all cross-registry collisions during prepare, before commit. Sorted node and edge keys are the only order passed to blueprint/materialization; IDs do not use allocation order.

## 6. V1 finite graph contract and structural algorithm

Effective limits are fixed by `p10b.ruin-structure/v1`: 6–10 places inclusive; one entry; 5–19 unique directed connections inclusive (the generator emits a directed spanning backbone plus zero or more forward chords); at most 4 containment edges on any root-to-leaf chain. These are a v1 resource envelope, not universal LocalTopology limits. Every place is reachable from the entry by following outgoing connections; containment is not traversal.

**Algorithm, with no complete-layout templates:**

1. Create node 0 with key `place/000000`, marked as the sole entry. Draw `N = 6 + NextBelow("node-count", 5)`, then create nodes 1 through N−1 in ascending numeric order.
2. For each node i, draw its spanning-tree parent using `lo = max(0, i−3)`, `parent_i = lo + NextBelow("tree-parent/" + i as four-digit decimal, i−lo)`. Add exactly one directed connection `parent_i → i`. This gives a connected, acyclic spanning backbone while allowing different local branching shapes.
3. In ascending i, consider containment under the tree parent: if the parent's containment depth is below 4 and `NextBelow("containment/" + i, 4) == 0`, set i's parent to that tree parent and its depth to parent depth + 1; otherwise i has no containment parent and depth 0. The lower-index parent rule makes containment acyclic; the depth check bounds it.
4. Enumerate all ordered forward pairs `(i,j)` with `0 <= i < j < N` that are not already backbone connections, in lexicographic numeric order. For each pair, add directed chord `i → j` iff `NextBelow("chord/" + i + "/" + j, 4) == 0`. Stop considering pairs only when the connection cap 19 is reached. Since the tree has at most 9 edges, the total cap is always respected; to honor the 19 cap it is sufficient to stop at 19. The draw key binds the pair, so optional loops are reproducible independently.
5. Sort nodes by numeric key and directed edges by `(origin index, destination index)`; every generated edge has `origin < destination`. Assign traversal cost `1 + NextBelow("cost/" + i + "/" + j, 3)` (integer-valued float 1, 2, or 3). Use no connection type definition and no place type/content semantics in v1. Materialize the single entry, parent links and edges into the existing blueprint shape.
6. Validate the entire generated draft against §6 invariants, including reachable traversal graph, finite positive cost, exact counts, no self/duplicate directed edge, endpoint membership, unique IDs, acyclic containment/depth, and one entry. A validation failure rejects the request; no repair or silent clamping occurs.

This graph-growth process makes keyed structural choices at each node/possible edge and can produce many graph shapes. It does not select among stored complete graphs. Deterministic fixtures must find at least two distinct graphs over a fixed published seed/key matrix; do not require every pair to differ.

## 7. Private pre-start staging, atomic publication, and P12 boundary

The current code does not provide a private LocalTopology build transaction. `LocalTopologyBuilder.TryBuild` allocates sequential IDs and immediately commits to `LocalTopologyStore`; P10-A's `P10RuinLocalTopologyGenesis` and semantic owner index currently use DefinitionId and perform store/registry mutations before all later anchor/topology validation has completed. P9 `SpatialAuthorityStore.TryComposeGeography` privately validates its own pending geography before adding geography records, but that is not an atomic transaction spanning P9, site stores, identity registry and local topology. The final `SimulationBootstrapComposition` is assigned only at the pipeline's publish stage, which makes the candidate inaccessible through that public property before then, but does not roll back earlier internal store mutations.

P10-B must preserve the existing P9 stage order and add stage `p10b.genesis.ruin-topology/v1` after `p9.genesis.authored-geography/v1` and before `p9.genesis.authored-actors/v1`/final profile validation. The selected profile contract is `unity-authored-bootstrap/ruin-topology-v1`, an explicit extension of the P9 geography profile. For the selected P10-B profile, bypass the P10-A eager Ruin composition path; retain the P10-A composer as the separate compatibility profile. Carry the configured definition and stable key as input only, without registering the P10-B site in the earlier authored-world stage. Resolve the actual canonical LocationId/anchor from `genesisSpatialAuthority`; do not mint, replace or fixture-substitute geography. The P10 stage derives identities and graph, then creates `PreparedRuinGenesis` only. It may not call `ExplorableSiteStore.Add`, `RuntimeIdentityRegistry.RegisterExplorableSite`, `LocalTopologyStore.TryAddTopology`, allocate sequential IDs or mutate P9 geography.

Extend `SimulationGenesisPipeline` with an explicit dependency record for the P10 stage. Add `p10b.genesis.ruin-topology/v1`, generator ID/version, rules revision and effective request fingerprint to manifest provenance. At final validation, derive graph fingerprint as `lowercase-hex(SHA-256(Frame("p10b-graph/v1", RequestFingerprint, sorted record fields...)))`. Emit place records in key order with fields `"place", localKey, runtimeId, parentKey-or-empty, entry-0-or-1`; emit directed edge records in key order with fields `"connection", edgeKey, runtimeId, originKey, destinationKey, integerCost-as-ASCII-decimal`. Derive the final composed-profile fingerprint as `lowercase-hex(SHA-256(Frame("p10b.genesis-profile/v1", P9 profile fingerprint, RequestFingerprint, graph fingerprint)))` and publish it in the manifest. Never feed this final fingerprint back into the generator root. The private candidate holds the prepared site, topology, exact-ID objects and cross-store write set. Complete P9/P10 profile validation and verify every collision/relationship before commit. P9 geography remains in the unpublished genesis candidate; if P10 validation/commit fails, discard/fault the entire candidate composition, so no partial world is exposed.

At the existing `p9.genesis.publish/v1` boundary, call one `TryCommitPreparedRuin` coordinator. Its preflight checks all target stores and SiteInstanceId/topology indices, including registry-wide member ID uniqueness. It then applies the already validated batch using internal no-fail insertions under one synchronous publication guard, recording undo actions for every list, map and revision mutation. If any insertion unexpectedly fails, replay the undo journal in reverse and return failure; only after all insertions succeed is the batch marked committed and `SimulationBootstrapComposition` assigned. The operation never consumes shared RNG. Implement store `TryPrepare`/batch registration primitives; do not emulate atomicity by a sequence of existing public `Add` calls. The candidate bootstrap is faulted and remains unpublished on failure.

This is genesis composition only. After the first simulated boundary, edits require ordinary reviewed runtime mutation authority; P10-B adds no install, regeneration, retrofit, construction or runtime expansion API.

The site/topology owner must expose exact initial-state export/hydration/validation seams sufficient for eventual continuation and fork. Until the selected P12 profile explicitly supports and tests this owner, keep it excluded by construction from `UnityBootstrap-Daily-v1` or ensure that profile's admission rejects it with a tested diagnostic. Do not claim Save, load, replay or fork delivery from a P10-B design or implementation alone.

## 9. Test and review plan for implementation

1. **Identity/migration:** same archetype at different stable instance keys yields distinct site IDs; definition and Location IDs remain distinct; P10-A legacy profile still composes and resolves with its existing single-site behavior; global RuntimeIdentityRegistry rejects collisions.
2. **Determinism:** same compatible request across fresh runtimes gives byte/semantic-equal sorted places, containment, entries, connections, costs and IDs; reordered input collection has no effect; unrelated RNG consumption has no effect; different seed and different site key fixtures can yield different graphs; no assertion that all pairs differ.
3. **Algorithm range:** a bounded deterministic matrix of compatible seed/site inputs generates more than one valid graph; every result stays within configured finite limits and is not a selection from complete layout templates.
4. **Graph validation:** reject empty/missing entry, unreachable place, cross-site endpoint, duplicate IDs/directed edges, self-edge, invalid cost, containment cycle/depth violation, impossible parameter set, malformed revision and foreign Location/anchor.
5. **Atomicity:** induce invalid graph, site/member ID collision, stale/wrong P9 Location and late profile validation failure; assert no site/topology/member registrations, no partial genesis facts, and no shared RNG advancement. Successful commit publishes complete owner and graph together.
6. **Reconstruction gate:** assert effective seed/context, generator and rules revisions are included in profile provenance; assert the exact initial generated owner state is available to reconstruction seam or selected `UnityBootstrap-Daily-v1` rejects the owner. This is a required P10 implementation gate, not a P12 feature claim.
7. Run existing P10-A/P8/P9 composition regressions and `git diff --check`; independent review checks scope, determinism/replay sensitivity, identity migration and publication atomicity. No Unity tests were run for this documentation-only design.

## 10. Dependencies, exclusions, closure

**Hard dependencies:** promoted P9-B ordered genesis/profile provenance; P8 canonical Location/anchor and ExplorableSite contract; P10-A LocalTopology owner/build/store authority; compatible effective seed/rules identity available at genesis. Spatial tests or fixtures cannot replace selected-profile canonical Location resolution.

**Explicit exclusions:** second Ruin/second Location in the shipped proof; choosing pre-authored whole layouts; loot, traps, encounters, inhabitants, resources, exploration knowledge, RPG-system tables, dungeon-room content schemas; universal graph/dungeon engine; broad ruleset/mod format or loader; runtime construction/expansion; existing-world retrofit/regeneration; new travel/activity/actor mechanics; Save/P12 implementation; architecture or Phase State edits.

**Implementation-ready only after independent design review** confirms the P10-A compatibility mapping, v1 vectors/algorithm, and SiteInstanceId migration/transaction scope are implementable with selected genesis inputs/provenance and current LocalTopology constraints. Then dispatch implementation in an isolated branch; serialize integration on genesis composition and LocalTopology publication hotspots. Promotion and phase closure remain separate gates.
