**Purpose:** independent source audit for CORE-F architecture preparation. This is a migration map, not a final implementation review and not authorization to implement or promote. Scope is current-source reuse and the remaining .NET shared-source boundary for thread admission, advance eligibility, capture/export, staged restore, relationship integrity, and publication.

### A source-comment mismatch worth correcting in the integration record

The XML summary in ContinuationCensusProtocol.cs still says the protocol is not wired to a runtime. Exact b2 source disproves that wording: SimulationRuntime creates npcRosterCensusProtocol (SimulationRuntime.cs:2191), registers the live owner providers and operation IDs (:2146-2325), binds the owner thread, and uses the protocol for owner-vector/quiescence/epoch reads and operation scopes. The accurate limit is that the kernel does not issue DailyCaptureEligibilityToken; that private lifecycle lives in SimulationRuntime.

## Core reuse and the actual migration gap

The following source is already in the shared Core package and is reusable under its existing contracts: AtomicFileSlot, ContinuationWire, NumericProfileIdentity, P12ACompatibilityDescriptorV2 plus its strict bridge, SimulationCalendar, typed Daily-v1 effective definition values, stable identity primitives, and the promoted bounded population/genealogy sources. These primitives do not constitute an application host or P12 token/image/restore integration.

Two Unity-side sources have no lexical UnityEngine import, which does not establish compiled portability:

- ContinuationCensusProtocol.cs has no UnityEngine reference and supplies owner census, operation-scope, and mutation-epoch mechanics. It references concrete NPC/profile types in the current compile graph and is not an independently ready portable leaf. A bounded cut requires exact implementation tests and full type/member access closure. It does not own the current token lifecycle or establish that runtime entries cover every supported writer.
- SimulationTime.cs has no UnityEngine reference and already has an internal runtime dispatcher seam. Moving that clock alone does not preserve the Daily-v1 operation contract; its dispatcher must still be bound by the shared SimulationRuntime.

Neither source alone is a viable CORE-F host slice. This audit finds no independently useful capture protocol package smaller than the shared selected runtime/application closure: the identity token, epoch, lease, operation gates, 89-family census, C/D/E/F owners, and restore coordinator are mutually bound through current runtime and private owner identity. A leaf-only promotion may be a useful library primitive, but it must be described strictly as that primitive and cannot be used as a readiness or .NET-continuation claim.

For the actual host package, use the full selected Daily-v1 application closure:

1. Move the selected SimulationRuntime, admission context, lease, completed-token lifecycle, mutation-guard binding, operation and owner-provider registration into one Simulation.Core assembly with the selected domain owner writers and provider implementations.
2. Move the exact P12-A/C/D/E/F/G image, codec, source capture, detached staging, relationship validation and restore coordinator source into that assembly, retaining private/internal access. Keep selected owner semantics and writer/epoch joins on the same bytes in Unity and .NET.
3. Move only the host-neutral session gate, report/receipt state and composition needed by the selected graph. Leave TesteSimulacao, ScriptableObject parsing, Application.persistentDataPath, Unity logging/debug presentation, Unity thread capture, and scene/asset binding in the Unity adapter.
4. Reuse the existing Core v2 descriptor, then integrate typed host compatibility through P12AContinuationHeader, P12AContinuationImage, P12AContinuationCodec, P12AContinuationStore, and descriptor construction. Current P12 header/codec/store/factory still speak P12ACompatibilityDescriptor v1; the v2 type's existence alone is not .NET save/load. Preserve Unity v1 parsing/bytes and reject v1 Unity identity in .NET before candidate construction or slot mutation. Add the explicit-root injected file-operation overload to TryLoad; the current explicit load chooses SystemAtomicFileSlotOperations.Instance itself.
5. Build the fixed .NET host inputs from the same effective definition values and preserve same-host/same-build semantics. Validate Core and Unity against the same source bytes; keep the claim scoped to per-host compatible saves. Do not claim cross-host save interchange.

The Core extraction design's source-closure gate still applies: selected constructor/member/type edges and conditional branches must compile from the shared source. In particular, SimulationRuntime.cs imports UnityEngine and contains host-specific numerical/logical adapters; split only exact, reviewable adapters. Do not solve this with stubs, copied owner rules, broad InternalsVisibleTo, public Store exposure, or a file-count threshold.

## Evidence use and limitations

The P12 State/closure, current code, focused SimulationRuntimeAdmissionTests, P12-A codec/save/load tests, P12-G restore cases, and exact validation records support reusing the bounded Unity behavior where their source inputs match. This audit does not recompute the complete P12 evidence manifests or independently re-run tests. It also does not turn the 89 family rows, 24 route rows, selected fixture counts, or source-reference graph into exhaustive reachability proof. Use the current owner writer matrix and capture-target crosswalk row-by-row, rooted source traces, exact input identity, and preserved finite tests when assembling the host migration proof.

**Disposition:** preserve P12 behavior intact in a single shared selected-runtime/application package. Existing Core persistence/clock/value primitives are reusable. A smaller census-kernel or clock leaf can be promoted only as a primitive with no capture/restore capability claim. The end-to-end Unity-to-.NET path remains dependent on the full selected host source closure and the v1-header/v2-host-identity integration above.
